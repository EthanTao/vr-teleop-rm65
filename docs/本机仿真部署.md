# 机器人断电时的本机仿真

本机运行链为 Windows → WSL2 `RM65-Servo` → Docker → **InputAdapter → PoseTracking → MoveIt Servo → JTC → mujoco_ros2_control → MuJoCo**。无手柄与 PICO 共用控制节点、参数和模型，只切换输入源。**机器人及配套板无需通电，仿真不连接 RM65 控制器。**

## 已配置的环境

| 项目 | 当前配置 |
| --- | --- |
| Windows | Windows 11 家庭版；约32GB内存 |
| WSL | 官方3.0.3；WSL2内核6.18.54.1 |
| Linux | Ubuntu22.04.5，发行版 `RM65-Servo`，磁盘 `D:\WSL\RM65Servo` |
| 容器 | Docker Engine29.9.2 + Compose5.6.1，安装在Linux内；未装Docker Desktop |
| 显示 | 默认WSLg + MuJoCo；RViz按需开启；软件OpenGL，无GPU/USB/机器人设备映射 |
| 控制代码 | 与板端使用同一镜像、launch和参数，只切换设备接口 |

旧 Ubuntu20.04 已完整导出并校验，再注销；`D:\WSL\Ubuntu2004` 及 `Ubuntu2004-Source` 残留已清理。可恢复副本位于项目 `build/archive/wsl-pre-servo-20261025/`，不是在运行的旧环境。WSL运行时通过微软签名/公开SHA-256校验后修复安装，没有自动重启或修改BIOS。

MuJoCo 与此前 GenericSystem 的分层证据保留在[2026-10-26日志](logs/2026.10.26.md)，三个入口及无手柄控制台的本轮验证见[2026-10-27日志](logs/2026.10.27.md)。界面显示、软件仿真、实体 PICO 和真机验收分别记录；本机仿真不能批准真实执行。

## 日常启动

根目录只有三个日常入口，无交互选择菜单：

| 入口 | 行为 |
| --- | --- |
| `启动无手柄仿真.cmd` | 明确选择 manual，打开 MuJoCo，终端打印本机控制台地址 |
| `启动PICO仿真.cmd` | 明确选择 pico，检查局域网并准备本项目的转发，再等待手柄 |
| `启动真机.cmd` | 包装既有板端链；无参拒绝，不连接网络 |

也可在 Windows 根目录明确指定输入，`-CheckOnly` 只预览，不启动 WSL / Docker / ROS 或修改网络。PowerShell 脚本省略输入时默认 manual，不弹出选择：

```powershell
.\scripts\setup\start_simulation.ps1 -InputSource manual
.\scripts\setup\start_simulation.ps1 -InputSource pico
.\scripts\setup\start_simulation.ps1 -CheckOnly
```

底层 `teleop.py` 命令保持可用：

```powershell
python teleop.py --mode sim --input manual
python teleop.py --mode sim --input manual --no-viewer
python teleop.py --mode sim --input manual --target wsl --rviz
python teleop.py --mode sim --input mock # 离线自动演示，不是日常交互入口
python teleop.py --mode test
```

已注册 `RM65-Servo` 时，sim/test 自动走本机。`--target wsl` 可显式指定；`--target remote` 才使用原来的机器人板。WSL模式直接读取当前Windows仓库，不SSH、不远端同步、不复制另一套控制逻辑。

默认只打开 MuJoCo，RViz 关闭。无手柄模式待服务就绪后，点击终端中的 [http://127.0.0.1:8766](http://127.0.0.1:8766) 打开控制台；入口不自动打开浏览器。按住 Space + 方向键，或持续按住页面方向按钮移动。控制台显示实际仿真 q/dq、TCP、目标、误差与运行状态；具体按键和操作限值见[操作手册](仿真操作手册.md#2-无手柄控制台)。

`--input mock` 保留一次约15秒的毫米级平移/小角度旋转演示，随后松 Grip 并保持；CLI 省略输入时仍使用 mock。MuJoCo 以有限力矩的位置执行器计算动力学，运动跟随、IK 和模型保护仍由相同 Servo 控制节点完成。

需要检查 TF、模型或 TCP 目标时，加 `--rviz`；该选项只支持 WSL sim，不能与 `--no-viewer` 同用。`--no-viewer` 关闭 MuJoCo 窗口和 Foxglove，manual 控制台仍由输入节点提供。`--simulator mock` 改用 GenericSystem 做控制图诊断，控制逻辑相同；如需图形反馈须显式加 `--rviz`。测试模式在无网络容器内运行，不打开 GUI。

物理参数位于 `ros2_ws/src/rm65_servo_teleop/config/mujoco.yaml`。当前假设理想重力补偿，位置执行器增益和厂商URDF惯量未做实机辨识，不用于报告真实接触力或实际跟踪性能。场景只含机械臂和地面，手/相机支架/充电枪/插座待加入。模型在容器启动时从同一修正后URDF生成，关节轴、d6及TCP不另维护第二份。

遥操作保持名义1倍物理速度；ROS控制与超时仍使用真实流逝时间。MuJoCo `/clock` 用于记录物理时间和独立进度检查。**暂停物理超过200ms、物理时间倒退或引擎退出会关闭整条控制图，恢复须重新启动。** 原始记录附带 `simulation_model.json`，标明引擎、模型/网格哈希、物理假设，并记录 `/clock`；它不是实体机器人数据。

首次需要下载/构建；后续依赖缓存保留，源码和XR SDK配置完全匹配时直接复用镜像，不访问镜像仓库。源码变动只重编相关层。日志直接写入当前Windows仓库的 `build/experiments/`。Ctrl+C退出当前会话；不要同时启动两份同名仿真容器。

## 真实PICO输入

电脑端已完成真实SDK编译、官方PC Service启动、Windows局域网TCP代理及软件协议联调。**头显目前不在身边，真实设备连接、追踪质量与手柄方向尚未验收。**

头显回来后，双击根目录 `启动PICO仿真.cmd`。入口会选择当前唯一在线WiFi地址，显示需要填入PICO的地址，唤起专用WSL，准备仅属于本项目的TCP63901规则，再打开MuJoCo并等待手柄。更换WiFi后，入口只迁移本项目自建的旧地址规则；检测到不属于本项目的规则时停止并报错。网络配置这一步会出现Windows管理员权限提示，控制程序仍使用普通用户身份。

在PICO的XRoboToolkit客户端中手动填入入口显示的Windows地址和端口63901，选择Controller并开启Send；先松开右Grip，再按住跟随，松开保持。机器人和配套板均无需通电。先做低幅度六向移动和旋转，确认方向，再检查松Grip和停止发送均能停止模拟关节。

也可从PowerShell运行：

```powershell
.\scripts\setup\start_simulation.ps1 -InputSource pico -CheckOnly
.\scripts\setup\start_simulation.ps1 -InputSource pico
# 多个WiFi地址时，显式指定与头显同网的本机地址
.\scripts\setup\start_simulation.ps1 -InputSource pico -ListenAddress <本机实际LAN_IP>
# 专用WSL发行版名称变化时，显式指定 -Distro
```

仅需程序本身、已自行配置网络时，仍用 `python teleop.py --mode sim --target wsl --input pico`；此命令本身不配置Windows转发。没有头显时程序保持等待，关节不会自行运动。

默认WSL NAT下，PICO与Windows电脑处于同一局域网，手工填写Windows局域网IP及TCP63901。局域网入站需要Windows TCP代理指向WSL eth0地址，并有仅限局域网的防火墙规则；WSL重启后IP变化时须更新代理。manual 和 mock 不读取局域网接口，也不配置这一转发。

底层脚本是 `scripts/setup/connect_pico_wsl.ps1`。在管理员PowerShell中可先用 `-ListenAddress <本机实际LAN_IP> -WhatIf` 预览，再移除 `-WhatIf` 应用；`-Remove` 只撤销该脚本自建的代理/防火墙规则。它不修改全局网络模式、不重启服务、不覆盖其他代理。2026-10-26已实际配置并从Windows所选局域网地址通过代理发送带合成标记的协议数据；未从另一台局域网设备或实体头显验证。

此前使用 GenericSystem 的无头显软件测试共接收764个标记帧，最后一帧Grip=1；断流前仍处于跟随，最后一帧后约0.213秒关闭使能，随后501个关节采样保持不变。这不是本轮 MuJoCo 的停止结果，也不是物理停止时间或网络最坏延迟保证。

若无输入，先确认PICO与电脑同网、填的是入口显示的Windows地址、Controller/Send已开启；校园网隔离终端时需改用双方可互通的网络。查看 `/rm65/input_status` 可区分无输入、输入超时、须先释放Grip和TF问题；状态包含TF/反馈年龄及最近一次TF失败原因。服务退出会报错并结束当前仿真，不会回退到模拟手柄。


官方PC Service主连接是TCP63901；发现广播为UDP29888，每5秒发送，SDK内部gRPC为127.0.0.1:60061。容器内广播不会自动变成Windows局域网发现，所以使用手工地址，不声称自动发现已打通。[官方常量](https://github.com/XR-Robotics/XRoboToolkit-PC-Service/blob/v1.0.0/RoboticsService/DeviceConnectionManager/Manage/Manage_global.h#L13-L16)、[SDK本地连接](https://github.com/XR-Robotics/XRoboToolkit-PC-Service/blob/v1.0.0/RoboticsService/PXREARobotSDK/PXREARobotSDK.cpp#L300-L309)、[微软NAT局域网转发](https://learn.microsoft.com/en-us/windows/wsl/networking#accessing-a-wsl-2-distribution-from-your-local-area-network-lan)。

## 环境维护

Docker安装脚本是 `scripts/setup/install_docker_wsl.sh`；只接受专用Ubuntu22.04 WSL2及systemd，不运行控制容器、不删除Docker数据。不要把新栈装回旧Conda环境。

2026-10-27发现专用WSL的系统时间约每32秒跳变，导致真实关节时间戳回退检查失败；同次日志中多个进程的墙钟一起回退约1.1秒。当前已确认 Hyper-V 的 `timesync_implicit=Y`，并按[Ubuntu官方WSL校时说明](https://ubuntu.com/wsl/docs/stable/explanation/time-sync/)关闭该发行版中重复的 `systemd-timesyncd`，保留Windows宿主校时。处理后保持原断言，完整14组ROS仿真检查通过；没有修改Servo/JTC参数或放宽时间保护。证据见[当日日志](logs/2026.10.27.md)。

仅在专用WSL、确认上述Hyper-V同步已开启且复现同类问题后，使用 `wsl -d RM65-Servo -u root -- systemctl disable --now systemd-timesyncd.service`；不要用于原生Ubuntu或真机板。需撤销这项环境配置时，使用同一发行版的 `systemctl enable --now systemd-timesyncd.service`。`timedatectl`显示NTP服务inactive只表示内部NTP未运行，不表示Hyper-V宿主同步被关闭。

新WSL若未启动，可直接运行启动命令唤起；不需先手动SSH或启动机器人。恢复供电后，`启动真机.cmd` 要求显式 `-UdpIp`、有效 `-HardwareValidation` 与人工 `-LiveAck "RM65 LIVE VALIDATION"`；无参列出缺项后退出。`-CheckOnly` 只验证参数并预览，Dry Run 仍会连接真实控制器读反馈。详见[现场验证](真机安全与故障处理.md)，不得从本机仿真推导真实运动批准。
