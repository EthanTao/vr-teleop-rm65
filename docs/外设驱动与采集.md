# 灵巧手与 D435i：离线准备和现场接入

2026-10-28：仓库已增加独立灵巧手驱动、D435i 采集、配置模板与文件校验。真实设备默认关闭；本轮不连接手或相机、不做真实动作或标定、不更新板端正在运行的控制环境。实际测试结果见[当日日志](logs/2026.10.28.md#peripherals)。

## 本机可用的内容

| 部分 | 行为 | 仍需现场完成 |
| --- | --- | --- |
| ROH RS485 驱动 | 独立 TCP 连接，经 RM65 `port=1` 读取身份、六通道位置/状态/电流/角度；显式授权后只写六通道速度、位置 | 型号后缀、供电接线、RS485/协议、节点地址、完整身份/固件、末端 Modbus 配置 |
| 手任务与按键 | 复用既有 prepare→grasp→人工确认→保持→人工插入标注→释放；独立工作线程，不阻塞 ROS 回调 | 张开/抓枪姿态、速度和通道范围；故障停机、持物失联与手/臂通信并发验证 |
| D435i 采集 | 指定序列号，RGB8 `(H,W,3)` + 原生 Z16 `(H,W)`；默认640×480@30Hz；可选另存对齐深度 | 序列号、固件/SDK兼容、USB协商/设备映射、实际流组合、深度质量 |
| 记录 | 图像 NPZ、逐帧元数据、手反馈/事件、全文件 SHA-256 清单；异常/丢记录标记不完整 | 曝光—机器人时间关系、手眼标定、任务质量及训练数据验收 |

ROH-LiteS001 没有独立力传感器。电流、堵转和人工确认不构成接触力或抓取成功的实测依据。D435i 的 IMU 本版不采集。

## 不接设备的演练

仓库根目录，用现有 Python 环境执行（本地工具不要求 ROS 或 RealSense SDK）：

```powershell
python -B scripts/tools/hand_control.py demo --profile ros2_ws/src/rm65_servo_teleop/config/hand_mock.yaml --output build/hand-offline.jsonl
python -B scripts/tools/camera_control.py record --source mock --profile ros2_ws/src/rm65_servo_teleop/config/camera.yaml --root build/experiments --seconds 3
python -B scripts/tools/camera_control.py verify "上一步输出的完整采集目录"
```

手演练输出拒绝覆盖；相机每次创建新的 `sensors_<UUID>` 目录。mock 图像/时间戳/手反馈都明确为合成数据。mock 手不含抓取接触物理。

在现有 Linux ROS/WSL Docker 环境中构建独立镜像：

```bash
docker compose -f docker/compose.peripherals.yml build
docker compose -f docker/compose.peripherals.yml run --rm peripherals \
  ros2 launch rm65_servo_teleop peripherals.launch.py hand:=mock camera:=mock
```

若默认PyPI直连不可达，可显式设置环境变量 `RM65_PIP_INDEX=https://pypi.tuna.tsinghua.edu.cn/simple` 再构建；依赖版本保持固定。本轮使用该镜像索引完成实际验证。

此 launch **不启动机械臂**。手与相机各运行一个进程，仅发布 `/rm65/hand/status`、`/rm65/hand/events`、`/rm65/camera/status` 及 ROS 诊断。不发布机械臂目标、轨迹、使能或停止命令。与现有 sim 图联调时，共用 `ROS_DOMAIN_ID`，主图保持 `--hand off`，避免两套手节点竞争相同话题。真实会话不混入 mock 话题。

现有 `rm65_hand_command` 可操作 mock；真实手模式还要求命令参数 `--live-ack "ROH FIELD MOTION VERIFIED"`。收到 accepted 只说明逻辑接收，须观察后续反馈和阶段。退出 sidecar 不代表机械臂或实体手已经停止，手/臂故障联动仍是现场验收项。

## 现场灵巧手接入顺序

1. 先核对后缀（CAN版不能用此驱动）、供电、接线、RS485 115200/8N1、协议主版本和从站地址。继续使用[只读预检](灵巧手接入.md#现场只读预检准备)，默认仅预览，明确 `--execute-readonly` 才联网；未配置末端 Modbus 时读失败，工具不自动配置电源/Modbus。
2. 将 `hand_field.template.yaml` 复制为 `build/field/hand.yaml`，填写现场数据：包括寄存器1000..1005的**完整六字身份**。先运行 `hand:=readonly hand_profile:=/field/hand.yaml`；不需要填写动作预设或把写入验证标志设为真。
3. 实现已经支持真实速度/位置写入，但 `hand:=live` 在启动前检查 `field_verified`、`presets_verified`、`stop_and_concurrency_verified`、完整速度和范围、有效动作预设及显式口令。模板默认不满足检查。现场先做独立空手动作/停止与并发验证，保留证据后再填写这些项目；**不能把 mock 预设复制成现场值**。
4. 已核对身份后，启动/轮询仍不发送任何动作；只有显式 prepare/grasp/release 请求才发速度和位置。要求最近0.5秒内六通道停止反馈，速度写入后再次检查新鲜度。超时、坏包、失败/错路由应答均关闭并锁存，不自动重连或重试。堵转、电流保护、力控到位和未知状态均按异常处理。

身份匹配只证明该响应与配置一致，不自动确认实际型号、接线、固件兼容或工具配置。多块 Modbus 读数不是原子快照，记录保留各块收包时刻，反馈年龄取最旧一块；ACK 不是到位。TCP JSON 没有请求事务号，独立串行连接仍不能证明所有固件或控制器多连接行为都兼容。

## 现场相机接入顺序

SDK 在独立外设镜像里固定为 `pyrealsense2==2.58.1.10581`、`numpy==1.26.4`，同时安装 `libusb-1.0-0`，不安装到宿主或修改当前控制镜像。此版本选择用于可重复准备，不代表已验证现场固件。ARM64 Python3.10 两个wheel已下载至 `build/validation/peripherals-20261028/arm64-wheels/` 并记录SHA-256/检查AArch64 ELF；仍需另做目标运行验证，不能用x64或包结构检查代替板端ABI验收。

```powershell
# 默认不导入 SDK、不枚举设备
python -B scripts/tools/camera_control.py inspect
# 以下在现场连接相机且已安装对应 SDK 的环境执行
python -B scripts/tools/camera_control.py inspect --execute-readonly
```

枚举输出型号、序列号、固件、USB类型和可用 profiles。工具不升级固件、复位设备或改写校准。将 `camera.yaml` 复制到 `build/field/camera.yaml` 并填写序列号；不支持的流组合直接报错，不自动改分辨率或切换设备。

相机接在 Linux 板时，先在宿主确认 USB/UVC 权限和实际 SDK 后端，再按 `docker/compose.camera-usb.template.yml` 收窄映射。模板要求显式设置真实 USB 路径，UVC 后端还须核对实际 `/dev/video*`；它不是已经验证的通用设备映射。不使用 privileged，也不自动安装宿主 udev/内核补丁。

将 `build/field` 挂载为 `/field:ro` 后，现场独立采集示例：

```bash
docker compose -f docker/compose.peripherals.yml run --rm peripherals \
  ros2 launch rm65_servo_teleop peripherals.launch.py \
  camera:=realsense camera_profile:=/field/camera.yaml run_label:=lab-session-001
```

CLI 的 `record --source realsense` 默认预览，追加 `--execute-readonly` 才启动实际图像流。ROS 的 `camera:=realsense` 是显式采集选择。串号缺失、设备型号不符、缺帧、序号/时间戳重复或倒退、时钟域变化均结束采集，不自动重连。

## 记录、配对和资源边界

每个外设进程独立创建采集目录，`metadata.json` 保存配置、设备信息及 Linux boot 单调时钟标识；`records.jsonl` 保存事件/帧索引；图像在 `frames/*.npz`，保留原始 RGB、原生深度以及可选派生对齐深度。相机保存 depth scale、两流内参、depth→color外参、帧号、各自设备时间戳与时钟域、可用曝光元数据和主机收帧时刻。手状态/事件分别保留候选、准入、发送尝试、应答、真实读数和人工阶段。

采集结束后 `manifest.json` 覆盖所有数据文件的大小和 SHA-256。校验器拒绝不完整清单、文件篡改、孤立帧、丢失文件和软链接。写盘线程使用有界队列；默认8帧，RGB-D原始数据约12MiB（不含对齐时），可选对齐约17MiB，另有当前帧及 NumPy/文件开销。队列满、写盘错误、断连和关闭超时均使记录无效。主机磁盘容量仍需现场按任务时长预留。

现行 arm journal 已订阅相机状态，保留采集目录、run_label和设备/时间信息；它不代替相机目录的完整性清单。采集结束要回收并分别校验两个目录，保留共同 run_label。

```bash
python scripts/tools/camera_control.py pair --capture <相机采集目录> \
  --journal <机械臂journal目录> --output <新配对表.jsonl> --max-delta 0.05
```

离线配对仅接受相同 Linux boot 时钟、完整真实/只读 arm journal 和非合成相机；只取去重后的真实 UDP feedback，不取目标轨迹。配对按**相机主机收帧时间与 ROS 收包时间**找最近候选，超出预算保留未配对行。这是 `host_and_ros_arrival_only`，**不是曝光同步**；输出始终 `training_ready=false`。Windows或跨主机时钟未知时拒绝配对，后续需要实测时钟桥接、延迟和误差。`rs.align` 只做像素对齐，手眼标定仍未提供现场结果。

帧复制、可选对齐和写盘复杂度 O(HW)，队列空间 O(QHW)。手计算 O(6)，命令队列最多8条、事件缓存最多256条；网络由单个独立工作线程执行。CPU、内存和磁盘仍与其他进程共享；当前测试不构成板端负载、50Hz期限、物理停机或训练数据质量验收。

协议依据：[RealMan JSON Modbus](https://develop.realman-robotics.com/robot/json/modbus/)、[OYMotion Gen1](https://oymotion.github.io/ROHand/ROH-Protocols/OHandModBusRTUProtocol_Gen1/)、[Gen2](https://oymotion.github.io/ROHand/ROH-Protocols/OHandModBusRTUProtocol_Gen2/)、[RealSense官方Python示例](https://github.com/realsenseai/librealsense/blob/master/wrappers/python/examples/align-depth2color.py)。
