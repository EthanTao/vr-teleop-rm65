# 2026.9.10 修改记录

## 1. RM65 可选官方连续 IK 真机链路

### 1.1 修改原因

Placo 继续只服务于 RM65 的 URDF 仿真。真机若希望明确控制 IK 分支，不能复用与控制器实测 TCP 存在较大偏差的 URDF/Placo 解算结果，因此新增睿尔曼官方 API2 连续 IK 适配链路。

现有推荐真机链路 `movep_follow` 保持默认，不因本次修改自动切换。新链路必须显式选择，并且在现场完成坐标系和 J3 非零软限位确认后才能构造控制器。

### 1.2 新增数据流

```text
XR 目标位姿
  -> 现有笛卡尔速度/加速度与工作空间限制
  -> rm_algo_ik_remote(T_target, q_udp)
  -> RM65-B 关节范围检查
  -> 单周期关节步长检查
  -> movej_follow
```

其中 `q_udp` 是当前周期 UDP 关节反馈，作为连续 IK 的种子，以降低跳到另一 IK 分支的风险。任何 SDK 缺失、IK 返回失败、非法数值、越过关节范围或单周期步长过大都会触发现有硬停止与故障锁存逻辑。

### 1.3 代码修改

- 新增 `xrobotoolkit_teleop/hardware/realman_official_ik.py`：延迟加载官方 Python SDK，完成 `wxyz` 四元数目标到 4x4 齐次矩阵的转换，以及关节角弧度/角度转换。
- 扩展 `RealmanRM65Interface`：新增 `movej_follow` 关节目标发送，沿用项目已有的关节符号和零偏换算。
- 扩展 `RealmanRM65SafeTeleopController`：新增 `official_ik_movej_follow` 模式，使用 UDP 关节反馈作为 IK seed，并在下发前执行关节限位和单周期步长检查。
- 扩展真机入口：新增 `--official-ik-tool-or-work`、`--official-ik-frames-verified` 和 `--official-ik-j3-soft-limit-verified` 参数。
- 增加官方 IK 适配器、控制器成功/失败/超步长/dry-run、安全门槛和 `movej_follow` 单位换算测试。
- 同步 `README.md`、`CLAUDE.md` 和 `docs/VR_TELEOP_HANDOFF.md`。

### 1.4 使用边界

- 默认仍为 `--motion-command movep_follow`。
- 可选模式要求目标运行环境安装与 RM65-B 控制器匹配的睿尔曼 API2 Python SDK；该二进制依赖没有加入 `pyproject.toml`。
- `--official-ik-frames-verified` 只表示操作者已核对控制器当前 work/tool frame 与程序目标位姿定义一致，程序不能自动替代现场核对。
- `--official-ik-j3-soft-limit-verified` 只表示操作者已在官方环境中配置并验证 J3 非零软限位；程序没有擅自写入现场关节软限位。
- 首次运行必须使用 `--dry-run`。此时会真实执行 IK 与关节步长检查，但不会发送运动目标。

### 1.5 验证边界

- 主机全量回归：`223 passed in 0.56s`。
- Python 编译检查：`python -m compileall -q xrobotoolkit_teleop scripts tests` 通过。

- 本次没有连接机械臂或执行任何真机运动。源码测试、目标环境依赖检查、真实 SDK 验证和真机验收是不同证据，不能互相替代。

## 2. 仿真侧接入同一官方 FK/IK 链路

### 2.1 修改原因

真机新增官方连续 IK 后，原仿真仍只能使用 Placo IK，无法在真机前观察官方算法输出的关节构型、分支连续性和 J3 零位风险。本次为仿真入口增加可选官方后端，同时保留 Placo 默认行为。

### 2.2 数据流与职责

```text
q_home
  -> 睿尔曼官方 FK 得到 Grip 末端锚点
  -> XR delta 生成官方坐标中的目标位姿
  -> rm_algo_ik_remote(T_target, q_sim)
  -> RM65-B 关节范围 + J3 排除区 + 单周期步长检查
  -> 将 q_target 写入 URDF/Placo robot wrapper
  -> Meshcat 显示关节构型
```

在 `--ik-backend official` 下，Placo 不参与 FK/IK，只负责 URDF 状态容器和 Meshcat 可视化。不能用 Placo URDF 的末端坐标作为官方 IK 锚点，否则会再次混用已知不一致的两套运动学。

### 2.3 修改文件

- `xrobotoolkit_teleop/hardware/realman_official_ik.py`：增加官方 `rm_algo_forward_kinematics` 封装，返回米制位置和归一化 `wxyz` 四元数。
- `xrobotoolkit_teleop/simulation/realman_official_ik_teleop_controller.py`：新增官方 FK/IK 驱动的 Meshcat 仿真控制器。
- `xrobotoolkit_teleop/simulation/realman_official_ik_guard.py`：新增无图形依赖的 RM65-B 关节范围、J3 默认 ±5° 排除区和单周期步长检查。
- `scripts/simulation/teleop_rm65_sim.py`：增加 `--ik-backend placo|official` 及官方 IK 参数；默认仍为 `placo`。
- `teleop.py`：增加 `--sim-ik-backend placo|official` 并透传到容器内仿真入口。
- 增加官方 FK、仿真 guard、控制循环写入和启动参数转发测试；同步 README、操作手册、交接文档和项目规则。

### 2.4 安全与能力边界

- 官方仿真后端要求 `home_joint_deg` 的 J3 位于默认 ±5° 排除区之外；运行中进入排除区或关节单周期跳变过大时保持上一帧，并输出 `[OFFICIAL IK HOLD]`。
- 官方后端不执行 Placo 自碰撞任务或 Placo 关节速度裁剪；若请求对应开关会直接拒绝启动，不会静默忽略。官方 IK 输出只通过 RM65-B guard，避免 URDF 限位二次修改官方关节解。
- 官方仿真验证的是算法 FK/IK 与关节连续性，不证明 URDF 末端坐标、现场 work/tool frame、安装角、工具负载或物理碰撞安全。
- 当前开发机没有 Meshcat、Placo 和睿尔曼官方 SDK；实际目标容器启动与 Meshcat 页面检查仍待完成。

### 2.5 验证状态

- 主机全量回归：`229 passed in 0.57s`。
- Python 编译检查：`python -m compileall -q xrobotoolkit_teleop scripts tests teleop.py` 通过。
- 新增验证覆盖：官方 FK 单位/四元数、official 后端选择、当前关节 seed、IK 输出写入显示状态、RM65-B 限位、J3 排除区、单周期步长和一键启动参数透传。
- 修改文件行宽检查和相关 Markdown UTF-8 检查通过。

## 3. Docker 容器映射 RM65 实时 UDP 反馈端口 8089（预防性改动，非本次根因，见章节 4）

### 3.1 修改原因

真机启动时 `RealmanRM65SafeTeleopController._startup()` 在 1 秒内未收到任何有效 RM65 UDP 反馈，触发 `no valid RM65 UDP feedback received during startup` 硬停止。排查确认容器用默认 bridge 网络：TCP 8080 是容器出站主动连接，NAT 默认放行所以 preflight 正常；而 UDP 8089 是机械臂入站主动推送，必须显式端口映射才能进入容器。原 `docker-compose.yml` 只映射了 63901 与 9090，`Dockerfile` 也未 `EXPOSE` 8089，导致反馈包只到达宿主机而进不了容器。

### 3.2 修改文件

- `docker/docker-compose.yml`：`xrobo-vr` 服务 `ports` 新增 `- "8089:8089/udp"`（附注释说明为 RM65 realtime UDP feedback）。
- `docker/Dockerfile`：`EXPOSE` 增加 `8089/udp`，与 compose 映射保持一致。

### 3.3 边界与注意

- 本次仅解决容器网络层。机械臂控制器侧的「实时状态推送」目标 IP/端口仍需在示教器/控制器里预先配置（程序不会自动修改机械臂 UDP 配置，见 `docs/2026.9.9.md`），目标应是运行程序主机上机械臂可直达的网卡 IP 的 `8089`，并确认报文含 `joint_status.joint_speed`、`joint_position`、`waypoint` 与错误码。
- 端口映射改动需重建容器（`docker compose down && docker compose up -d`）才生效；`teleop.py` 仅 `docker exec` 复用已有容器，不会补端口。

### 3.4 验证状态

- 本次未连接机械臂，未在远程板重建容器执行真机验收。
- 待办：在远程板重建容器后，用 `sudo tcpdump -i any udp port 8089 -n` 确认机械臂已在推送；再运行真机入口确认打印 `[INFO] home pose captured from UDP ...` 而非启动硬停止。二者（容器端口映射 + 控制器侧推送配置）缺一不可。

## 4. 修复 RM65 UDP 反馈 `err` 字段格式解析（本次真正根因）

### 4.1 根因

真机启动报 `no valid RM65 UDP feedback received during startup` 的真正原因不是网络，而是解析 bug：

- 实测板子 eth0 = `192.168.10.100`、机械臂 `192.168.10.18` 直连（ping 0.8ms）。机械臂**一直在往 `192.168.10.100:8089` 推送 UDP**，并经 docker 端口映射成功进入容器——当前容器为手动 `docker run` 启动（`Config.Labels` 为空），`HostConfig.PortBindings` 已含 `8089/udp`。
- 但 `realman_udp_feedback._parse_error_codes` 假定 `err` 字段是对象 `{"err_code": [...]}`；RM65-BI V1.7.0 控制器实际推送的是数组 `"err": [0]`。解析器对每个包抛 `ValueError("err must be an object")`，被 `_receive_loop` 计入 `invalid_packet_count` 丢弃，`latest()` 恒为 `None`，启动阶段约 1 秒内拿不到有效反馈而硬停止。

章节 3 的 docker 端口映射改动实为预防性：本地 `docker-compose.yml` 确未映射 8089，但现场容器是手动 `docker run` 且已映射，对本次故障不起作用；保留该改动以防将来改用 compose 重建时丢失映射。

### 4.2 修复

- `xrobotoolkit_teleop/hardware/realman_udp_feedback.py`：`_parse_error_codes` 同时兼容 `err` 为数组（三代控制器真实格式）与对象（旧假设格式）；数组分支直接把元素当错误码、过滤掉 0，语义与旧 `err_code` 分支一致。
- `tests/test_realman_udp_feedback.py`：新增数组格式参数化用例，以及一份完整 RM65-BI V1.7.0 真实报文解析测试（`err`、`joint_status`、`waypoint`、`state` 字段全量）。

### 4.3 验证状态

- 本地全量回归 `234 passed in 0.62s`（含新增用例）。
- 容器内用真实报文验证 parse 全链路通过：`joint_rad`、`tcp_xyz_m`、`tcp_quat_wxyz`、`joint_speed_rad_s`、`arm_error_codes=()` 均正确，`err:[0]` 判为无错误。
- 待办：真机入口完整启动验收，确认打印 `[INFO] home pose captured from UDP ...`；并留意 `joint_speed` 单位换算（代码按三代控制器 0.01 deg/s 假设，静止时 J6 原始值 1）在运动时超速检测是否合理，必要时现场标定。
