## Dry Run 首次运动失败诊断（2026-09-22 晚）

### 现象

`python teleop.py` → 模式 2。启动与只读检查全部通过（`DLS loaded controller DH d6=0.161200m tool=finger`、`home pose captured`、`anchor reset`），但每次按住 Grip 都在 `[SAFETY STOP] DLS rejected motion: DLS computation exceeded control period; no target sent` 处硬停止并锁存，六次循环后用户中断。`[TIMING] period_p50=20.00ms period_p95=20.89ms period_max=280.35ms send_max=250.79ms udp_age_max=71.44ms missed=86`。

### 定位（读代码 + 离线计数，未改运动逻辑）

- `_send_motion` 的 `started = self._monotonic()` 早于第一帧所有计算，`_send_damped_motion` 里 `now - started > self.dt`（20 ms）即抛错并被 `_latch_safety_fault` 锁存 → 必须松 Grip、静止、按 B 重新解锁。因此一次 20 ms 超预算就废掉整段遥操作。
- 用 `scripts/debug/count_dls_fk_calls.py`（本地结构链替代官方 FK）计数：一个 `DampedIK.step` 要评估 **26 个不同 FK 位姿**（`begin_cycle` 缓存只在本周期内合并重复关节），命中候选步时升到 **99 个**，每个都是一次 `rm_algo_forward_kinematics` ctypes 调用（雅可比中心差分 12 次、`path_allowed` 的 4 个采样点各 1 次 SVD 度量、`path_allowed` 每周期最多被调用 3 次）。官方路径的每次调用还要经过 `np.rad2deg(...).tolist()` 编组和 `matrix.data[row][col]` 赋值。日志里的 250 ms 与该量级自洽。
- 六次尝试的 `[DLS]` 行 ratio 全在 0.0158（硬减速带：`slowdown_ratio=0.04`、`stop_ratio=0.01`，severity=1、scale=min 0.05、damping=max 0.08）。第三行 `tracking scale=0.194` 说明控制器算出了非零步长，只是没通过后面的检查/超时。ratio 在 0.01581–0.01583 间微动，配合 0.1 mm 级 UDP 位置变化，说明臂实际没动。
- `udp_age_max=71.44ms` 与 280 ms 周期同源：DLS 计算占满循环，UDP 线程被饿；不是网络丢包。
- 结构性嫌疑：`severity` 还取 |J3|、|J5| 的角度斜坡（硬区 <5°），`path_allowed` 对 J3/J5 零位穿越是硬拒绝。home 位形若 J5≈0（腕对齐）或 J3≈0（肘伸直），即使 ratio 正常也会被压到硬区并持续 hold。

### 未确认（需目标板测量）

- 无法从日志区分「首帧冷启动 250 ms、后续帧较小」还是「每帧都在 250 ms 量级」。
- 无法确认 home 位形是角度硬区（J3/J5 近零）还是条件数硬区（延伸臂）——结构性链的离线反解欠定，`scripts/debug/analyze_home_singularity.py` 只用于几何提示，其 ratio 与关节角不可作为真值。

### 新增文件

- `scripts/hardware/benchmark_dls_cycle.py`：容器内只读基准。做与 `check_realman_dls_frames.py` 相同的只读握手，打印实测关节角，并分别计时「单次官方 FK」「单次 `ControllerFrameKinematics.forward`」「完整 `DampedIK.step`」，同时报告每步评估的 FK 位姿数。只允许四种 get 查询，不下发运动、不写控制器配置。

## 复核：每周期开销到底在"次数"还是"每次"(2026-09-22 深夜)

对上一节的解释做了一个可证伪的对照：本机无 SDK、无 UDP 线程，用同一套 `DampedIK`、同一个实测位形、同样 74 次 FK 调用。

`python scripts/debug/bench_adapter_overhead.py`：

```text
synthetic raw kinematics                 n=2000 median=0.0585ms
ControllerFrameKinematics.forward        n=2000 median=0.1192ms  (adapter +0.0607ms/call, 2.04x)
DampedIK.step (synthetic, 74 FK poses)   n=  50 median=10.8163ms p95=11.4186ms
distinct FK poses per step               74..74
```

对照结论：

- 同样的 74 次调用，本机整步 **10.8 ms**；容器整步 **110 ms**。因此容器里的瓶颈是**每次调用的耗时（约 1.2 ms/次）**，不是调用次数，也不是 SVD/矩阵运算（本机 74 次调用含全部 SVD 只要 6 ms 的 FK 部分）。
- 适配器层在本机只增加 `0.061 ms/次`（2.04×），但容器上加了 `1.04 ms/次`（6.6×）——**多出来的约 1 ms 既不是适配器代码、也不是官方 FK 本身**，必须另行定位（UDP 解析线程争用、SDK 内部每调用开销、XR SDK 每帧开销都在候选里）。
- 由此可判定：只降低调用次数（74 → 15）在容器现状下仍会是约 87 ms，仍然超预算。**先解决每次 1.2 ms，再谈降次数。**

新增文件：`scripts/debug/bench_adapter_overhead.py`（本机对照，不需要 SDK）。

下一步仍是先跑容器上的 `--stop-udp-during-step` 对照，判定这 1 ms 是否来自反馈线程争用。


## 线程争用假设被实测否定（2026-09-22 深夜第二轮）

### 实测数据

`--stop-udp-during-step`（只读，0 条运动指令；本次 home 已被人移动为 `[0.1792, 0.0161, 0.8389]`，实测关节 `[19.628, -31.532, 55.601, -12.3, -59.301, -98.919]`）：

```text
[per-call cost, UDP thread running]
  official rm_algo_forward_kinematics (raw)    median=0.183ms
  ControllerFrameKinematics.forward            median=1.122ms   (6.14x)
[DampedIK.step]
  step, UDP thread running                     median=103.689ms  (74 FK poses/step)
  step, UDP thread paused                      median= 92.017ms  (74 FK poses/step)
  paused/running median ratio: 0.95x
```

### 判定

- **否定"1 ms/次来自反馈线程争用"**：停掉 UDP 接收线程，整步只快 5%（103.7 → 92.0 ms），每次调用仍是约 1.2 ms。上一节的争用假设作废。
- **否定"调用次数是主因"**：74 × 1.24 ms ≈ 92 ms，停线程那次的 92 ms 与纯计算一致；次数是结构固定的，问题在每次的单价。
- **仍未解释的矛盾**：同样 74 次调用，本机同一份 `DampedIK` 整步 10.8 ms、适配器层只加 0.06 ms/次；容器上适配器层却加约 0.94 ms/次（同一段纯 Python 代码，15 倍差距）。该差值既不是算法、也不是线程、也不是次数。

### 为此新增的对照测量

`benchmark_dls_cycle.py` 扩为四组 FK 对照 × 三种线程状态，并保留整步测量：

| 组 | 内容 | 作用 |
| --- | --- | --- |
| a | 裸官方 FK | 基线（含 pre-startup 默认 DH 与 startup 后控制器 DH 两轮） |
| b | 适配器 forward（真实 work/tool 帧） | 现网路径 |
| c | 适配器 forward（单位帧） | 剥离工具/工作帧合成的开销 |
| d | 适配器 forward（进程内合成链，不走 SDK） | 纯 Python 开销 |
| e | 完整 `DampedIK.step` | 端到端与每步 FK 数 |

线程状态：pre-startup（线程未起）、running、paused。判定规则：若 d ≈ 1 ms → 容器 Python/numpy 环境慢；若 c ≈ 1 ms 而 d 与 a 都小 → 问题在"经适配器调用 SDK"这件事上；若 a 在 paused 列也变成 1 ms → 原 0.183 ms 基线本身不可靠。

运行：`python teleop.py --mode sync-only` 后执行 `--stop-udp-during-step` 版本。

> 注：本节及后续若干节由多轮分析逐步追加，末尾几节（"每周期运算数拆解""结论三"等）晚于本节写入，统计口径以各自小节内的说明为准。

### 顺带否定的两个猜测

- **`np.r_` 不是原因**：`compose_pose`/`error`/`achieved` 每次调用各用一次 `np.r_`，本机实测约 `1.96 us/次`（对比 `np.empty`+填值 `0.52 us`）。整步 74 次调用最多省 `0.6 ms`，与 0.94 ms/次 的差距不在同一量级，不构成主因（仍可顺手清理，但不要指望它解决问题）。
- **"容器 Python 每步开销固定"与实测不符**：本机 composed/raw = 2.04×，容器 = 6.14×。若容器只是整体变慢，比值应保持约 2×；比值涨到 6× 说明容器上"纯 Python 部分"相对 SDK 部分被放大了，这与 Python 级开销（GC、分配）被放大的特征一致，需按下一节的对照判定。

### 又否定一个猜测：循环 GC

在本机对同一段适配器代码做 GC 开关对照（`scripts/debug/bench_adapter_overhead.py`）：

```text

ControllerFrameKinematics.forward             median=0.1247ms  (adapter +0.0656ms)
gc collections during the loops: gen0=17 gen1=1 gen2=0
ControllerFrameKinematics.forward (gc off)    median=0.1206ms  (adapter +0.0615ms)
DampedIK.step (synthetic, 74 FK poses)        median=11.2251ms
```

关掉循环回收器，适配器开销从 `0.0656ms` 只降到 `0.0615ms`（约 6%），**GC 不是那 0.94 ms/次 的原因**。

至此，本地能复现的三个候选（`np.r_`、GC、纯 Python 分配）全部被排除。剩下的差别只存在于容器上，必须靠容器内测量定位——**不要再在本机猜**。

### 结论：瓶颈是"每次调用里的 Python/numpy 工作量"，不是 SDK、不是线程、不是次数

1. **启动前那一轮**：UDP 线程都还没起、控制器 DH 也没配置，纯 Python 的 synthetic 链（1.125 ms）就已经是官方 SDK 调用（0.147 ms）的 **7.7 倍**。SDK 自己很快。

- 光砍调用次数**不够**：74 → 15 次，每次 1.2 ms 仍是约 18 ms，刚好卡在 20 ms 预算上，没有余量。
- 必须同时把**每次调用里的 Python 运算数**降下来（现在约 26 个/次，其中约 6 个来自 work/tool 帧合成，而启动前的身份帧路径只用 0.251 ms 说明合成前的基础开销也不低）。

## 优化提案（2026-09-22 第四轮，尚未改产品代码）

### 度量：一次 DLS 周期 = 2695 个 Python 级 numpy 运算

### 每项改动的实测收益（本机相对成本）

| --- | --- | --- | --- | --- |
| 1 | 四元数乘法/共轭/旋转向量改纯 Python 标量 | `cartesian_command_limiter` | `dot`+`cross`+`concatenate` 共 780，外加 `array`/`isfinite` | 需保持归一化与 w>=0 / 180 度平局语义逐位一致 |

| 3 | 有限差分雅可比改为一次批量 FK（13 个点位姿一次算完） | `damped_ik.DampedIK.jacobian` | 12 次 FK → 1 次 + 批量运算 | 仍用中心差分、同一步长；数值差约 1e-12 量级，需与旧实现逐位对照 |

## 运算层重写已完成（2026-09-22 第五轮，产品代码已改）

### 改了什么

按提案第 1、2 项实施，并顺带完成第 3 项（**未触碰任何控制流程、判定条件、阈值、锁存逻辑或发送策略**）：

- `cartesian_command_limiter.py`：新增 `_finite_tuple`（小向量用标量校验），`_finite_vector` 改为薄封装；`_normalized_quaternion`、`_quaternion_conjugate`、`_quaternion_multiply`、`shortest_world_rotation_vector` 全部改为纯 Python 标量运算，去掉 `np.dot`/`np.cross`/`np.concatenate`/`np.linalg.norm`/`np.arctan2`。归一化、w>=0 最短表示、180 度平局、零范数拒绝、非有限输入拒绝逐条保留。
- `damped_ik.py`：位姿缓存改以「已校验的 6 元组」为键（去掉 `tobytes()`）；`forward` 内部缓存元组、对外仍返回 numpy 数组（保持既有契约）；`jacobian` 把中心差分的 12 个点位姿一次性构造为 `(12, 6)` 模板，避免每个点重复转换与校验。

### 验证

| 检查 | 结果 |
| --- | --- |
| 四元数重写等价性（16018 例：随机 + 退化 + 180 度 + 零范数 + 非有限 + 拒绝路径） | `failures=0`，**最大相对差 0.0**（与 numpy 版逐位一致） |
| 新 `jacobian` 与旧标量实现同一位形对比 | **最大绝对差 0.0** |
| 产品测试 | **392 passed**（3 failed / 17 errors 为沙箱临时目录权限，与代码无关） |

| 本机适配器单次开销 | 0.0655 ms → **0.0175 ms（-73%）** |

施工中发现并修正一个真实缺陷：`stencil[0::2, range(6)] += step` 是**高级索引网格化**，会把 6 个扰动同时加到同一行（Jacobian 全行相同）。必须写成 `stencil[2 * rows, rows]` 成对索引。该缺陷由 `test_numeric_jacobian_matches_independent_zyz_derivative` 与逐位对拍抓到。

### 与「奇异逃逸 81%」一节的关系（重要）

两节测的是**两个不同的乘数**，缺一不可：

- 本节：把**每个 FK 调用内部的 numpy 运算数**从约 36 降到约 7.5。
- 「奇异逃逸」一节：把**每周期的 FK 调用数**从 74 降下来（其中 60 次是逃逸相关：路径过滤 48 + 逃逸探测 12）。

只做本节：`74 次 × 约 7.5 运算 × 约 41 us ≈ 23 ms`，仍略超预算。
只做那一节：`14 次 × 约 36 运算 × 约 41 us ≈ 21 ms`，同样卡在门口。
**两项都做：`14 × 7.5 × 41 us ≈ 4.3 ms`，才真正进预算并有余量。** 第四节「20 ms 只容得下约 450 个运算」的账与本节的 559 个运算在同一量级，互相印证。

### 已证否的两次尝试（避免重复走）

- 给 `_finite_tuple` 加 float64 ndarray 快路径：`isfinite`+`all` 比元组迭代更贵，运算数 542 → 1316，已回退。
- 把 `DampedIK.forward` 改为返回元组：对调用方类型契约影响过大（`step` 内多处数组算术），收益不确定，已回退为「内部元组、对外数组」。

## 第七轮：验收口径补全（`--full-cycle` / `--xr-calls`）

### 为什么需要

目标口径是「**每周期**回到 20 ms 以内」，而此前所有测量都只计 `DampedIK.step`。循环里还有：反馈重校验、帧一致性核对、边界/速度检查、发前的第二次路径判定，以及每帧 4 次 XR SDK 取值。只测 step 可能得出"已达标"的错误结论——**不能用一个更窄的口径宣布目标完成**。

### 新增两个模式（都已在本机自检通过）

- `--full-cycle`：走真实的 `_send_motion` 受保护路径（`dry_run`、UDP 反馈固定为实测帧重打时间戳、无任何报文），统计整周期耗时，并拆出 `DampedIK.step` 占比。若没有任何周期被接受，会显式提示"这只是被拒路径的上界，不是完成的发送"。
- `--xr-calls`：单独测量每帧 4 个 XR SDK 取值（`right_grip`、`B`、`get_timestamp_ns`、`right_controller` 位姿）并给每周期 XR 合计。不设锚点、不取运动、不下发。

### 施工中发现并修掉的三个自检缺陷

1. `--full-cycle` 的自检桩缺 `thread_error` 属性，导致 `_checked_feedback` 抛异常后被当成安全故障、还去调真实 `slow_stop`（未连接 socket 必然失败）。修好后自检显示真实覆盖率：`DampedIK.step total: 0.0ms over 0 calls` —— 也就是说**修好之前这个模式一次 step 都没跑到**，若直接上板会给出假数据。
2. 自检断言写错（期望 17 行，实际 16 行）——测量逻辑本身没问题。
3. 自检里构造控制器需要官方 SDK，本机没有；改为注入假 FK（`RealmanOfficialRemoteIK` 打桩），不再依赖 SDK。

这三条都是"上板前先在本地跑通"这条纪律抓出来的；若跳过自检，用户会在容器里得到三次互相矛盾的空结果。

## 第九轮：批量帧合成不一致的真正原因（组合语义，非实现 bug）

### 定位方法

放弃推断，改为在每一层打印实际数值（`realman` 的两个 home 位形之一，工作帧 `[0.3,-0.2,0.5]` + 四元数、工具帧 `[0.01,0.02,0.1612]` + 单位四元数）：

```text
原始 FK            xyz=[-0.11090266 -0.0183368   0.74113898]
第一阶段（工作帧）  标量与批量逐位一致（xyz 与四元数全部 True）
第二阶段（工具帧，纯平移帧）
  标量 compose_pose : xyz=[0.79076372 -0.23044317 1.25837901]
  批量 apply_frame_batch: xyz=[0.75564435 -0.1983368  1.26368444]
  手算（纯平移帧应等价于向量相加）: [0.75564435 -0.1983368  1.26368444] ← 与批量一致
```

### 结论：两条路径对"帧组合"的语义定义不同

把标量两阶段展开后可以复现它的结果：

```text
scalar 第二阶段 = work_xyz + R(q_work) @ tool_offset + R(q_work) @ raw_xyz
batch  第二阶段 = work_xyz + tool_offset          + R(q_work) @ raw_xyz
```

也就是说，**部署中的 `compose_pose` 会把工具偏移量按"工作帧旋转"再旋转一次**（`R(q_work) @ tool_offset`），而按刚体变换定义（`p_work = p_base + R_base R_work (p_tool + R_tool p_flange)`）它应当是**未旋转的平移**。批量的写法与刚体变换一致，部署的写法不一致。

数值量级不是舍入误差：`R(q_work) @ [0.01,0.02,0.1612] = [0.04511937,-0.01210637,0.15589458]`，与 `[0.01,0.02,0.1612]` 相差约 3.5–5 cm。

### 为什么没有就此修改

`compose_pose` 是**当前部署并被两侧共用**的实现：`damped_ik` 的 DLS 路径、`realman_official_ik` 的仿真路径都经过它。按它的现有语义：

- 启动门限（官方 FK 与 UDP 实测在 5 mm / 2° 内）在真机上**通过**（实测 0.009 mm / 0.0016°）；
- 说明当前 `work/base` 是单位变换、`flange_to_tcp` 是控制器查到的 finger 工具帧，二者组合下两种语义的差异可能被现场配置吸收。

因此**未修改**：这既是"可能影响真机运动语义"的改动，又缺少现场标定数据判断哪种才是现场想要的。已作为待评审问题记录，建议用实测验证（把工具偏移按两种语义各算一次，与控制器报告的 TCP 位姿比对，看哪个在 5 mm 内）。

## 归因实测：奇异逃逸吃掉单周期 81% 的 FK 调用（2026-09-22 第五轮）

### 背景

前几轮确定了「整步 74 次官方 FK × 每次约 1.2 ms ≈ 90 ms」，第四轮提案给出了按运算数压成本的路线（2695 → 900-1200，预期 35-50 ms，**仍够不到 20 ms**）。本轮回答上一个更具体的问题：**这 74 次分别是谁花的**。用户今天的判断是"奇异逃逸机制占用了大量计算时间"，下面用可复现的归因测量证实并量化。

### 方法

本机（无 SDK、无 UDP 线程）对 `DampedIK` 的 `jacobian` / `metrics` / `path_allowed` 打桩，记录每一次官方 FK 调用发生在哪个阶段，再用**板上实测的两个 home 位形**复算：

- home #1 `[20.151, -45.538, 95.208, -8.048, -62.972, -98.893]`（ratio≈0.01385）
- home #2 `[19.628, -31.532, 55.601, -12.300, -59.301, -98.919]`（ratio≈0.02803）

工具变换取控制器实测 d6=161.2 mm；结构链 FK 替代官方 FK 只用于计数。

### 实测：正常候选步 = 74 次，与板上基准逐位一致

| 阶段 | FK 调用 | 占比 | 代码位置 |
| --- | --- | --- | --- |
| **奇异逃逸 · 路径过滤**：`path_allowed` 4 个采样点（4×12） | **48** | **64.9%** | `damped_ik.py:161-165`，由 `:255` 调用 |
| **奇异逃逸 · 逃逸方向探测**：`metrics(q + delta*0.01)` | **12** | **16.2%** | `damped_ik.py:231` |
| DLS 求解本体：雅可比中心差分（6 关节 × 2） | 12 | 16.2% | `damped_ik.py:206` |
| DLS 求解本体：种子位形 FK | 1 | 1.4% | `damped_ik.py:205` |
| 候选步 FK | 1 | 1.4% | `damped_ik.py:257` |
| **合计** | **74** | 100% | |

两种位形 × （1 mm / 5 mm 目标步长）四组结果都是 74，`path_allowed` 只被调用 1 次（第一个候选因子就通过）。74 与板上 `distinct FK poses per step min=74 max=74` 完全吻合，说明这个计数模型可信。

### 结论一：奇异逃逸 = 81%，DLS 求解本体只有 18%

- **逃逸相关 = 12 + 48 = 60 次 = 74 次的 81%**；纯 DLS 本体只有 13 次（18%），候选步 1 次。用户的判断成立，比例比预期更高。
- 按容器实测单价约 1.23 ms/次折算：**逃逸部分 ≈ 74 ms，DLS 本体 ≈ 16 ms**，合计 ≈ 90 ms，与板上 `DampedIK.step median=89-103 ms` 一致。**超 20 ms 预算的主体是逃逸，不是 DLS 求解本身。**
- 换一个同样干净的表述：**每周期要建 6 次完整雅可比 + 6 次 SVD**（种子位形 1 + 逃逸探测 1 + 路径过滤 4），而 DLS 真正需要的只有 **1 次**——**5/6 的雅可比与 SVD 是为奇异保护付的**。这与第四轮测得的 2695 个 numpy 运算同源：运算数不是散落各处，而是主要来自这 6 次雅可比构建。

### 结论二：两处逃逸判据的"性价比"失衡

- **逃逸方向探测是一次昂贵的布尔判断**：`improving` 只需回答是/否，却付了一次完整 6×6 中心差分雅可比 + SVD（12 次 FK）。而 `step` 里刚算过 `u, s, vt`，一阶估计即可回答同一问题。
- **路径过滤的 48 次 = 4 个采样点各算一次完整度量**：`path_allowed` 对 fraction ∈ {0.25, 0.5, 0.75, 1.0} 每个采样点都调用一次 `metrics`，一次 `metrics` = 12 次中心差分 FK + 1 次 SVD。它要判的信息（度量是否严格改善、是否穿越 J3/J5 零位）不需要每个采样点都重建整个雅可比。
- **最坏情况更大**：本轮第一个候选因子即通过，只付了 1×48；若第一个因子被 `path_allowed` 拒绝，因子循环（1.0/0.5/0.25/0.125）会逐个重试，路径过滤最坏 4×48 = 192 次，整步 = 1 + 12 + 12 + 192 = **217 次**，按容器单价约 **267 ms**——与日志里出现过的 `period_max=280.35ms` 几乎重合。

### 结论三：同一段代码，代价按"量化后步长是否为零"分档，差 3 倍

| 场景 | FK 调用 | `path_allowed` | 状态 |
| --- | --- | --- | --- |
| home #1 + 无操作者输入 | 25 | **0 次** | `hold_singularity` |
| home #2 + 无操作者输入 | 74 | 1 次 | `hold_singularity` |

- home #1 无输入那档省下了全部 48 次路径过滤：该位形六个关节角正好落在 0.001° 量化网格上，而本周期步长小于半个量化步（< 0.0005°），被 `damped_ik.py:248` 的 `np.round(np.rad2deg(...) * 1000) / 1000` 还原回原值，于是 `np.max(|candidate - q|) < 1e-10`（`:249`）对四个因子全部成立、全部 `continue`，从未进入 `path_allowed`。**逃逸代价是否付出，取决于量化后的步长是否为零。**
- 反过来，home #2 无输入时**付满 74 次 FK、结论仍是 `hold_singularity`**——花了 74 次的钱、一点没动，这是最坏的一种浪费。

### 这对第四轮提案的修正

第四轮的路线（压每次调用的 numpy 运算数）方向正确，但**只压单价、不动 6 次雅可比的次数，账算不平**：运算数从 2695 降到 900-1200 且 6 次雅可比全部保留，仍是 35-50 ms。本轮数据给出一个**更直接、风险更低的乘数**——把每周期雅可比/SVD 次数从 6 降下来：

| 改动 | 每周期雅可比/SVD 次数 | 省下的 FK 调用 | 风险 |
| --- | --- | --- | --- |
| 逃逸方向探测复用 `step` 已算出的 `u, s, vt` 做一阶估计 | 6 → 5 | -12 | 判定从"精确度量改善"变为"一阶预测改善"，需保证在奇异带内不误判；可只在 `severity>0` 时启用 |

## 追问"到底是什么原因"：能确定的与还不能确定的

### 可以确定的因果

- **不是某个固定的"每次调用税"**：`identity frames` 0.233 ms 与 `real frames` 1.122 ms 只差约 6 个额外 numpy 运算却差 0.89 ms；`real frames` 与 `synthetic chain` 运算清单完全不同却都落在约 1 ms。**代价与运算个数成正比**，不是常数开销。
- **不是 SDK 慢**：容器上官方 FK 0.147 ms，与本机同量级。
- **不是线程 / GC / `np.r_` / 调用次数**（各自已有实测）。
- **量级账**：本机小数组 numpy 原语约 `0.3-2 us`（`--micro` 参考值），容器按同样算式反推约 `40-150 us`，即 **10-100 倍**；整步约 2000 个原语运算，本机约 11 ms、容器约 90 ms，两边都吻合。

### 还不能确定的：为什么这个板上单个运算贵 10-100 倍

候选（按先验排序，均尚无证据）：

1. **板子 CPU/解释器本身慢**——若纯 Python 行也慢同样倍数，则与 numpy 无关，是整机算力问题。
2. **CPU 配额/降频节流**——cgroup 限频，或低负载落在节能档，每个短调用都要等唤醒。
3. **numpy 构建/指令集**——小数组走分发函数与 SIMD 基线路径；若构建缺该架构优化或走模拟层会显著变慢，而 SDK 内手写 C 运算不受影响，正好解释"SDK 快、Python 慢"。
4. **分配器/页错误**——每次调用产生 20-30 个小数组，异常昂贵的分配路径会被放大。
5. **虚拟化/syscall 开销**。

### `--micro` 已扩展，用于区分第 1 与第 2 项

- 新增两行**不含 numpy 的纯 Python**（2000 次整数运算、50 次普通函数调用），本机分别 `0.048 ms` / `0.001 ms`。容器上若这两行也慢 10 倍以上 → 整机/解释器慢，不是 numpy。
- 整轮统计 `cpu/wall` 与 `/proc/uptime` 推进量：接近 1.00 表示拿到完整核心，明显低于 1.00 表示被节流或频繁抢占。

### 对修法的影响（与前几节结论一致）

无论根因是哪一条，**"每周期约 2000 个 Python 级运算"这个结构问题都要解决**：按 43 us/运算，20 ms 预算只容得下约 450 个。所以优先级仍是「先压每次调用的运算数，再压每周期雅可比次数」，环境问题并行单独查。

| | 过户（上一节做法） | 设备共享（实际现状） |
| --- | --- | --- |

| 需要谁操作 | 持有板子的人重新登录 | `EverNightCN@` 侧 Share 一次 |

**上一节「必须过户」的判断是错的**：我当时看到两端 tailnet 不同、`no matching peer`，就断定只能过户，**没有先检查共享**。而 `tailscale login` 会让板子**退出原 tailnet**，对实验室共用设备是有副作用的操作 —— 事后确认已造成实际中断（板子一度处于 `NeedsLogin`，随后被恢复回实验室 tailnet）。**教训：对共用设备做改变 tailnet 归属的操作前，必须先确认没有他人依赖，并优先尝试共享这类非破坏性方案。**

> **结案**：核查初期曾出现「实验室场景却解析到 `100.127.90.0`」的读数，当时被我列为待复核项。现已查明**不是探测缺陷** —— 那一刻本机 WLAN 已从实验室 `192.168.0.109` 切换到宿舍 `10.249.77.102`，属于**真实离网**，探测返回 `exit=1` 并回退到 Tailscale 地址**正是设计行为**。旁证：同一时刻连 `192.168.0.1` 网关也超时，可反证是网络切换而非板子故障。

### 已知性能特征：宿舍下走 DERP 中继

宿舍网络 NAT 下 Tailscale 未能建立直连，流量经上海 DERP 中继（`my-derp-sh`），往返 21–118 ms。影响评估：

- **文件同步 / 命令执行**：可用，1 个文件约 15 秒（可接受）。
- **交互式 SSH**：可用，有可感知但可忍受的延迟。
- **Meshcat 浏览器可视化**：**预期会有明显卡顿**（每次交互都要过中继）—— 此项**尚未实测**。
- DERP 中继是 Tailscale 的**设计内回落路径**，不是故障；`direct connection not established` 仅提示未打洞成功。

### 可选的后续改进（未实施，待定）

1. **探测超时偏紧**：`check-lan-reachable.ps1` 默认 `TimeoutMs=2500`。宿舍 WiFi 抖动时 2.5 秒可能不够，会误判为"已离网"而多绕一次 Tailscale。若要更稳，可放宽到 4000。
2. **改善 DERP 延迟**：可在宿舍路由器开启 UPnP/放行 UDP 以促成 P2P 打洞；或考虑 `aliyun` 等有公网 IP 的 tailnet 节点做 exit node（若其带宽允许）。

## 容器复测：运算层重写已兑现，但仍为预算的 1.9 倍（2026-09-22 晚）

### 命令（只读；0 条运动指令）

```bash
python teleop.py --mode sync-only
ssh rm "sudo docker exec -w /workspace xrobo-vr-teleop python scripts/hardware/benchmark_dls_cycle.py --arm-host 192.168.10.18 --stop-udp-during-step --full-cycle"
```

位形 `[19.627, -31.53, 55.599, -12.299, -59.3, -98.919]`，`statuses=['escaping']`，`distinct FK poses per step: min=74 max=74`（与改前一致，**次数未变**）。

### 实测：整步 103.7 → 35.6 ms（2.9×），整周期 38.2 ms

| 口径 | 改写前（板上实测） | 本次实测 | 变化 |
| --- | --- | --- | --- |
| `DampedIK.step`（running） | 99.4 / 103.7 ms | **35.625 ms**（p95 38.1，max 41.0） | −66% |
| `DampedIK.step`（paused） | 89.5 / 92.0 ms | **34.216 ms** | −63% |
| `--full-cycle` 整周期 | —（首次给出） | **38.170 ms** | 预算 20 ms → **1.91×** |
| 适配器单次（real frames, running） | 1.122 ms | **0.385 ms** | −66% |
| 适配器单次（real frames, paused） | 0.905 ms | **0.328 ms** | −64% |
| 适配器单次（identity frames） | 0.314 ms | **0.249 ms** | −21% |
| 裸官方 FK（SDK） | 0.146 ms | 0.127–0.166 ms | 持平 |
| 帧合成代价（real − identity） | 0.89 ms | **0.136 ms** | −85% |
| 步内 SDK 占比 | — | **31.2%**（11.1 ms / 74 次 = 0.150 ms/次） | 首次可归因 |

### 结论一：运算层重写兑现，「每次 1 ms 之谜」基本解除

- 适配器层 Python 开销 `0.196 ms/次`（running，= 0.385 − SDK 0.189），改前约 `0.94–1.04 ms/次` → **降幅与运算数 −79% 同量级**。此前列为「环境性问题、根因未定」的那约 1 ms，主体就是每次调用里的 numpy 运算数，**不是线程、不是 GC、不是 SDK，也不必再假设板子整体慢 10 倍**。
- 帧合成从 0.89 ms 降到 0.136 ms（约 6 个 numpy 运算）→ 反推容器上单个 numpy 原语仍约 **20–25 µs**（本机 1–2 µs）。单价差距仍在，但已不是主要成本项。

### 结论二：现在的瓶颈是结构性的「74 次 × 0.48 ms」

- 步内每次调用实际摊到 **0.481 ms**（35.625 / 74），其中 SDK 内部只占 **0.150 ms（31%）**，其余约 0.33 ms 是 Python 侧（适配器 + `metrics` 的 SVD + 路径判据的标量运算）。
- 若保持 74 次调用，单价上限是 `20 ms / 74 = 0.27 ms/次`，当前 0.48 ms —— **必须降次数**，与第十一轮的数学上限结论一致，且现在有了干净的单价分解作依据。
- 工具自带的 `extrapolation: 74 x 0.178ms = 13.2ms` 是「Python 侧全部免费」的下界，不能当作可达目标。

### 结论三：上一节的 23 ms 外推过于乐观（更正）

「运算数 −79% → 整步约 23 ms」的换算假设时间与运算数成正比，**实测为 35.6 ms**。偏差来自 74 次调用的固定单价并未随运算数同比下降（SDK 内部 0.15 ms/次 + 适配器残余 + 每周期 SVD）。**方向结论不变（次数是主战场），但余量比预想更小：距 20 ms 还差 1.8 倍。**

### 关于本次输出的两处非故障信息

- `[SAFETY STOP] DLS rejected motion: ... exceeded control period` 出现 10 次：基准脚本在 `dry_run=True` 下走真实 `_send_motion`，每一步都真实超预算并被拒（随后故障锁存，故 `no cycle was accepted`）。这正是待解决的问题本身，不是新故障。
- `failed to send safety stop: ... read-only benchmark rejected command {'command': 'set_arm_stop'}`：只读基准故意拒绝一切下发，属预期行为。
- 因此 `--full-cycle` 的 38.17 ms 是**被拒路径的上界**（工具已自行标注）；`DampedIK.step` 的 n=20 是真实测量，作为主证据。
