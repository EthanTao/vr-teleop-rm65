## 1. 背景与动机

当前仿真（Placo IK）与真机（movel 笛卡尔）的输入映射，都是读取手柄位姿后，在按下 Grip 时把手柄位姿记为锚点，再把「当前手柄位姿 − 锚点位姿」的位移映射到机械臂末端。

期望：以手柄自身的相对移动驱动机械臂，而不是在以头显为原点的坐标系里计算手柄的绝对位移——担心头显转动/走动会污染手柄位移，导致机械臂误动。

## 2. 现状代码行为梳理

| 侧 | 位置 | 逻辑 |
|---|---|---|
| 仿真 | `xrobotoolkit_teleop/common/base_teleop_controller.py` 的 `_process_xr_pose()` | 读 `[x,y,z,qx,qy,qz,qw]` → 位置乘常量矩阵 `R_headset_world`、姿态做共轭旋转 → Grip 按下记 `ref_ctrl_xyz/quat` → `delta_xyz = (now − ref) * scale`，`delta_rot = quat_diff(ref, now)` |
| 真机 | `xrobotoolkit_teleop/hardware/realman_rm65_cartesian_teleop_controller.py` 的 `_process_xr_pose()` | 同上（独立实现、逻辑一致；常量矩阵用 `R_HEADSET_TO_WORLD_RM65_SIDE_MOUNT_HARDWARE`） |

两个事实：

- 严格说现在算的不是「绝对移动距离」，而是「相对 Grip 锚点的位移」（锚点式位置控制）。
- 常量 `R_headset_world` 只是把「头显坐标系朝向」静态旋转到「机械臂坐标系」，并不跟踪头显实时姿态。

## 3. 问题本质：不是「绝对 vs 相对」，而是「参考坐标系」

关键疑问：SDK（XRoboToolkit PC-Service + PICO app）返回的手柄位姿到底在什么坐标系里？

- **假设一（头显局部系）**：原点在头显、轴随头显转动。此时锚点与当前值分别位于「按下 Grip 那一刻」与「当前帧」两个不同的坐标系里，两者直接相减，头显转动/平移会混入手柄位移 → 用户担心的现象成立，必须改。
- **假设二（房间锚定系 / stage 系）**：重力对齐、原点固定（通常锚在 app 启动时头显位置）。此时现有锚点+delta 已经等价于「稳定世界系里的相对移动」，头显转动不污染（只有走动 / recentering 才会漂） → 用户担心的问题不成立，不必大改。

→ 必须先用实验确认是哪一种，这是整个方案的前置条件。
→ **2026.9.9 已查证官方文档：SDK 坐标系指向「假设二（启动锚定世界系）」，证据与解读见 §8；仍建议做一次零代码实测复核（§8.3）。**

### 无代码验证方法（复用现有开关）

1. 仿真：`XROBO_DEBUG=1` 每 2s 打印手柄 xyz；真机：`--log-motion-debug` 打印每帧 delta。
2. 手柄拿稳不动，只转动头部（左右 / 上下 / 歪头），观察打印的 xyz / delta 是否明显变化：
   - 明显变化 → 假设一成立，方案有必要；
   - 几乎不变 → 假设二成立，只需澄清坐标系与锚点语义，不必大改。
3. 身体平移（前倾 / 走动，手尽量不动），观察 xyz 变化，判断位移是否跟随头显原点。
4. 同时打印 `get_headset_pose()` 对照——`XrClient` 已封装该接口，无需新增 SDK 能力。

## 4. 两条候选技术路线

### 路线 A：头显位姿复合，把手柄位姿转到世界系后再算增量（「修坐标系」）

- 公式：`T_ctrl_world(t) = T_headset_world(t) · T_ctrl_headset_local(t)`；Grip 时记世界系锚点，delta 全在世界系计算；姿态增量必须同样复合，否则头显转动时手腕会翻转。
  - ⚠️ 查证后修正：SDK 返回的手柄位姿本身已是世界系（见 §8），本路线在真实语义下应改为**「手柄−头显」实时相对化**：`T_rel(t) = T_head(t)⁻¹ · T_ctrl(t)`，锚点与 delta 都建在 `T_rel` 上——这样才能同时消掉头显转动与整体平移。
- 优点：
  - 下游接口不变（`delta_xyz/delta_rot` 照旧进死区 / 滤波 / max_offset 钳制 → movel / IK），真机安全语义不被破坏；
  - 操作手感不变（仍是锚点式位置控制）；
  - 仿真 / 真机共享同一逻辑，改动集中。
- 缺点：
  - 引入头显位姿噪声（头显 tracking 噪声叠加到手柄上），需要滤波；
  - `R_headset_world` 常量矩阵的角色需重新定义，合成顺序错误会导致二次旋转 / 轴向错乱；
  - 若实测是假设二，再复合头显位姿等于重复计算头显运动，会把系统做坏——所以必须先验证坐标系。

### 路线 B：逐帧增量式（速度式「相对移动」，用户字面方案）

- 公式：每帧 `delta_frame = ctrl_now − ctrl_prev`，机械臂目标每帧 `+= delta_frame * scale`；手柄停机械臂停。
- 优点：
  - 摆脱「距锚点绝对位移」语义，头显原点长期漂移被逐帧差分消掉；
  - 3D 鼠标 / 速率控制是成熟模式，行业先例多。
- 缺点：
  - 帧间差分放大噪声，需要更强死区 / 滤波；
  - 若坐标系本身在转（假设一），相邻两帧差分仍混入坐标转动分量——问题只是变小、没有根除，彻底解决仍需 A 的复合；
  - 控制范式从位置式变速度式，手感完全不同（手柄回位机械臂停住、不回中）；
  - 真机安全钳制语义要重推：`max_offset_m` 从「距锚点上限」变为「每帧步长上限」，watchdog / 复位 / Grip 重新锚定逻辑都要复核；
  - 数据采集（DataCollector 记录 delta 作为 action）分布会变，新旧数据集不一致。

### 对比结论

- A 与 B 不互斥：A 是「修坐标系」，B 是「换控制范式」。
- 实测确认为假设一：先落 A（最小改动、保安全语义）；若还想要速度式手感，在 A 之上叠 B。
- 实测是假设二：A 不必做；B 作为独立的控制范式升级另行评估。

## 8. SDK 坐标系语义查证（2026.9.9 补充）

### 8.1 官方结论（原文出处）

来源：XR-Robotics/XRoboToolkit-PC-Service 官方仓库 README（英文）与 README-CN（中文）「PICO 设备 JSON 数据说明」章节。

中文原文：

> **坐标系**：左手坐标系，（X右，Y上，Z里），**坐标系的原点为启动应用时的头戴 Head 位置**。

英文原文：

> Coordinate System: (X right, Y up, Z in), **the origin is set as the head position when the application starts**.

配套要点（同一章节）：
- 头显、手柄、手势、全身动捕共享**同一个「世界坐标系」**（中文：全身动捕「均为和头戴设备数据相同的世界坐标系」；英文：Same world coordinate system as the headset data）。
- 位姿为七浮点 `x,y,z,qx,qy,qz,qw`，与 `XrClient` / `xrobotoolkit_sdk` 读取顺序一致；pybind / ROS 透传层不做坐标变换，即**文档语义 == 我们代码实际收到的数据语义**。
- 已知文档内部不一致：中英文对左右手系的描述互相矛盾（CN 全篇写左手系，EN 总述写 right-handed、controller 小节又写 left-handed），轴的方向性需以实测为准；本项目 `R_headset_world` 三套矩阵已经过仿真/真机方向验证，轴向极性不受此影响。

### 8.2 语义解读（对本方案的意义）

1. **坐标系在应用启动那一刻固定**（原点 = 启动时的头戴位置），之后**不随头显转动/平移**。头显自身的位姿也是在这个固定世界系里被跟踪并上报的量（示例数据在启动瞬间为 `0,0,0,identity`）。
2. 推论：**仅转动头部不会改变手柄在该坐标系中的坐标**。文档语义下「转头 → 手柄坐标变 → 机械臂误动」不成立；若实测观察到该现象，更可能是：转头带动肩/手轻微移动、追踪丢失重定位、或所用 app 版本行为与文档不一致——需实测确认。
3. 真正的残余问题：**操作员整体平移 / 前倾**时，手柄在「以启动时头戴为原点」的固定世界系中的坐标会随身体移动而变。按住 Grip 期间身体移动 → 手柄坐标相对锚点变化 → 机械臂移动。这是锚点式位置控制在任何固定世界系下的固有行为，也正是用户「以头显为原点算绝对位移」担忧的真实对应物（身体平移而非转动）。
4. 因此「以手柄相对移动为准」在真实语义下应实现为：**用每帧头显位姿把手柄位姿相对化**（等价于把参考系从「启动时的固定原点」换成「实时头显」）：
   `T_rel(t) = T_head(t)⁻¹ · T_ctrl(t)`，锚点与 delta 建立在 `T_rel` 上。
   这样转头、平移身体都不产生输入，只有「手相对头/身体的运动」驱动机械臂——与操作者直觉一致，也是路线 A 在此语义下的正确公式（替代原假设一写法）。
5. 可行性前提均已满足：`XrClient.get_pose_by_name("headset")` 已封装头显位姿；文档确认头显与手柄在同一世界系，可直接做相对化；头显噪声进入输入的问题由现有死区/滤波管线吸收。
6. 官方示例（`xr_mujuco_ur5e.py`）与多数参考实现都只做「锚点差、无头显补偿」，说明固定世界系 + 锚点差的方案在**站姿操作（脚不动、只转头动手）**场景下是可用的；本方案是对「会走动/前倾/转体」场景的增强，改动收益与必要性取决于实际操作习惯。

### 8.3 建议的零代码复核实验（结论已定，验证用）

1. `XROBO_DEBUG=1`（仿真）或 `--log-motion-debug`（真机）打印手柄 xyz；
2. 手拿稳不动、只转头 → 期望 xyz 几乎不变（验证文档语义）；

4. 同时打印 `get_headset_pose()` 对照，确认二者同系变化关系，为路线 A 的 `T_rel` 公式提供实测依据。

## 9. 设计原则：仿真映射必须符合人体直觉（2026.9.9 补充）

### 9.1 原则

**仿真是手感标定场**：仿真的用途是标定/调优遥操作手感，因此**仿真里的映射关系必须是符合正常人体直觉的参考系**（手柄上抬→工具端升高、前推→伸远、右推→向右，按真实安装语境下的期望方向验收）。真机侧的矩阵修正（`R_HEADSET_TO_WORLD_RM65_SIDE_MOUNT_HARDWARE`、`invert_tcp_xy` 等）是把这份"直觉参考"搬运到物理机器人上的适配层；**不能用真机适配矩阵反向定义仿真手感**，否则仿真失去"找手感"的意义。

### 9.2 代码现状与最终定案（2026-09-09）

- **最终决定（用户）**：机器人按 URDF **竖立显示**；手柄映射矩阵**回到改动前状态**——仿真入口与真机控制器均引用 `R_HEADSET_TO_WORLD_RM65_SIDE_MOUNT_HARDWARE`（行为与会话前完全一致，本轮仅做文档对齐）。
- **2026-09-09 补充确认（用户）**：该坐标映射关系**无问题** → 定案维持现状（`_HARDWARE` + 竖立显示），不切换矩阵；若日后实测发现反直觉，再按 §9.3 流程修正。
- 本轮实验并已按决定回退的内容：①仿真入口曾切到 `SIDE_MOUNT`；②基类曾新增 base 世界位姿参数 + 仿真侧装显示开关 `--side-mount-display`/`--mount-rpy-deg`。均已还原，不留死代码。
- 事实备忘：`SIDE_MOUNT`（2026-07-13 仿真验证）与真机 `invert_tcp_xy=True` 的有效映射等价；仿真用 `_HARDWARE` 且无二次取反，与 `SIDE_MOUNT` 水平轴相差 180°——该差异是否被操作者感知为"反直觉"只能由 §9.3 逐轴实测判定，**实测前不要盲改矩阵**。
- ⚠️ 待办（真机侧）：真机入口 tyro 默认 `invert_tcp_xy=False` 与 VR_TELEOP_HANDOFF/config 的现场值 `true` 不一致，待确认默认口径（记录规范见 §10）。
- 注意：仿真画面直接加载官方 URDF（竖立模型），与真机侧装朝向不同；"直觉"验收须放在真实安装语境下定义，否则容易误判。

## 11. Placo、RM65 官方 IK 与 MoveL 的责任边界（2026-09-09 讨论补充）

> 状态：方案讨论，本轮未修改控制代码，也未进行真机验证。

### 11.1 核心判断

- Placo 并非只适合全身机器人；它可以求解固定基座 6DoF 串联机械臂。本项目仿真侧已使用 `KinematicsSolver` 和 `mask_fbase(True)`。
- RM65 是非冗余 6DoF 机械臂。只做单末端位姿逆解时，Placo 的多任务 QP 能力通常用不充分；真机若引入外部 IK，优先评估与实际型号参数匹配的睿尔曼官方算法库。
- 当前推荐真机链路已更新为 `XR delta -> 安全限速 -> send_movep_follow_xyz_quat() -> TCP/JSON movep_follow`，并保留显式 `movel` 回退。两条路径都只发送笛卡尔末端目标，不发送外部关节角或 `joint_refer`，因此当前真机仍不使用 Placo IK；关节解算与执行由 RM65 控制器内部完成。

### 11.2 IK 与 MoveL 的区别

- 单次 IK 只完成“目标末端位姿 -> 一组关节角”。
- 原生 MoveL 会在笛卡尔直线上生成多个中间位姿，并由控制器逐点求 IK。
- “外部 IK 求 `q_target` 后调用 MoveJ”可以选择终点的肩-肘-腕构型，但末端中间轨迹不保证为直线，因此不等价于 MoveL。
- “终点存在 IK 解”不代表整条 MoveL 可执行；中间路径仍可能遇到关节限位、奇异点、工作空间边界或 IK 分支跳变。

### 11.3 后续候选方案

| 场景 | 候选方案 |
|---|---|
| 仿真与自定义多约束研究 | 继续使用 Placo |
| 真机普通位姿逆解 | `rm_algo_inverse_kinematics()`，以 current 关节反馈作 `q_in` |
| 远距离目标或需要选构型 | `rm_algo_inverse_kinematics_all()`，按当前关节距离、限位余量和分支滞回筛选 |
| VR 连续末端跟随 | 当前实现为 `movep_follow` + 安全限速 + UDP 独立反馈；`rm_algo_ik_remote()` 仅作为备选设计，切换前须确认现场 API/控制器版本、输入周期、关节下发通道与停机语义 |
| 环境避障路径规划 | 使用 MoveIt2 运动规划链；IK 插件本身不等于避障规划 |

### 11.4 风险与验证边界

- 既有“末端方向正确但中间关节运动异常”是在原高频 MoveL 链路下观察到的现象，可能与 IK 分支、`q3=0`/`q5=0` 附近奇异或重复 MoveL 重规划有关，但仍是待真机验证假设，不是已证实根因；新 `movep_follow` 路径也尚未完成真机验收。
- `r` 只影响笛卡尔段交融，不负责选择 IK 构型，单独调整它不能根治分支跳变。
- 切换外部 IK 前，先核对控制器、算法库与 RM API 版本；再按“算法回放 -> 仿真 -> 主机测试 -> 低速小范围真机”分层验证。
- 在上述证据补齐前，不把现有 `movel` 直接替换为未验证的关节流式控制。

## 12. 真机防超速安全控制第一版（2026-09-09）

### 12.1 要解决的问题

真机遥操作时，手柄输入会直接形成机械臂末端目标。原推荐路径虽然有死区、平滑、工作空间边界和故障停止，但还存在四个关键缺口：

1. `move_v=30` 对首次真机调试偏激进；
2. 只限制“目标位置”，没有明确限制每秒最多移动多远、每秒速度最多增加多少；
3. 主控制循环通过 TCP 同步查询状态，查询与下发相互阻塞，循环周期抖动时容易形成目标堆积或突跳；
4. 已经实现的限速器、输入跳变检查和 UDP latest-only 反馈没有接入推荐入口，旧单文件入口还能绕开它们。

本版目标不是证明“机械臂绝对不会超速”，而是建立一个**默认低速、命令有界、反馈独立、异常立即锁存、不能自动恢复**的第一道软件安全链。

### 12.2 新的数据流

```text
XR 手柄位姿
  → 时间戳/单帧跳变检查
  → 侧装坐标映射与 Grip 锚点
  → TCP 线速度/角速度 + 线加速度/角加速度限制
  → movep_follow 连续轨迹目标（TCP 只负责下发）

RM65 实时 UDP 状态（只保留最新一帧）
  → 新鲜度、控制器错误码、关节角合理性
  → joint_speed 关节超速、TCP 跟踪误差
  → 正常松手：软停止
  → 安全异常：硬停止 + 故障锁存
```

这里的 UDP（User Datagram Protocol，用户数据报协议）用作**独立反馈通道**：机械臂控制器主动把最新关节角、关节速度、TCP 位姿和错误码推送到运行程序的主机 `8089` 端口。程序只读取最新一帧，旧帧不会排队补执行。UDP 可能丢包，所以本版不假设每一帧都会到达，而是用 `0.20 s` 新鲜度看门狗：运动中超过该时间没收到新反馈就硬停止。

程序不会自动修改机械臂 UDP 配置。上机前必须在控制器/示教器侧把实时推送目标设为运行本程序的主机 IP、端口 `8089`，并确认报文包含 `joint_status.joint_speed`、关节位置、`waypoint` 和错误信息；缺少关节速度时启动失败，不能降级为“无超速检测继续运动”。

### 12.3 第一版保守参数

| 参数 | 默认值 | 作用 |
|---|---:|---|
| `motion_command` | `movep_follow` | 连续跟随绝对 TCP 目标；活动循环不等待运动 ACK |
| `move_v` | `5` | 仅在显式回退 `movel` 时使用，原值为 30 |
| `control_rate_hz` | `50 Hz` | 每 20 ms 生成一次有界目标 |
| TCP 最大线速度 | `0.05 m/s` | 末端一秒最多平移 5 cm |
| TCP 最大线加速度 | `0.40 m/s²` | 限制速度突增，减少冲击 |
| TCP 最大角速度 | `0.25 rad/s`（约 14.3°/s） | 限制末端旋转速度 |
| TCP 最大角加速度 | `1.20 rad/s²` | 限制旋转速度突增 |
| 平移时姿态抑制 | 默认关闭 | `suppress_rotation_during_translation=False`，允许平移与姿态同步跟随；保护开关仍保留 |
| 单帧 XR 平移/旋转跳变 | `0.05 m` / `0.26 rad` | 超过即认为追踪跳变并停车 |
| UDP 反馈超时 | `0.20 s` | 运动中反馈过期即停车 |
| 关节超速阈值 | RM65-B 各关节型号最大速度的 `10%` | J1/J2 为 18°/s，J3～J6 为 22.5°/s |
| 故障解锁静止阈值 | 每个关节 `≤1°/s` | 防止机械臂仍在运动时重新使能 |

上述值是**源码默认设置，不是真机实测结论**。首次运动仍应额外使用 `--max-offset-m 0.03`，把 Grip 锚点附近的总平移范围收紧到 3 cm；现场确认平稳后再逐项放宽，不能一次同时提高多个上限。

### 12.4 停止与恢复规则

- **正常松开 Grip**：发送 `set_arm_slow_stop`（软停止），让机械臂受控减速；同时清空锚点和限速器状态。再次按 Grip 时，必须用最新 UDP 实测 TCP 位姿重新建锚点，避免沿用旧目标跳动。
- **安全异常**：反馈超时、关节超速/越界、控制器错误、TCP 跟踪误差、XR 超时/跳变、目标越过 XYZ 边界或通信失败时，发送 `set_arm_stop`（硬停止）并锁存故障。锁存后不再发送运动目标。
- **故障恢复**：先完全松开 Grip；确认 UDP 反馈新鲜、没有错误、所有关节速度不高于 `1°/s`；再按一次 B。不能仅靠松开/重新按 Grip 自动清故障。
- **B 键复位**：非故障状态下仍用于平滑返回启动时从 UDP 记录的 TCP 位姿；复位目标也经过相同速度/加速度限制和看门狗。

## 13. 恢复平移与姿态同步 6-DoF 跟随（2026-09-09）

### 13.1 用户决定与行为边界

用户决定恢复原来的同步 6-DoF（Six Degrees of Freedom，六自由度）遥操作：按住 Grip 后，手柄相对锚点的三轴平移增量和三轴旋转增量同时映射到 RM65 末端目标。

改动前的真机推荐路径并非彻底关闭姿态，而是默认启用 `suppress_rotation_during_translation=True`：安全控制器根据手柄线速度计算 `_current_rotation_gain`，平移速度越高，旋转增量衰减越强；高速平移时姿态跟随可接近零。另一个独立开关 `freeze_rotation` 默认一直为 `False`，本次没有修改。

本次恢复后的控制语义：

```text
XR pose [x, y, z, qx, qy, qz, qw]
  → Grip 锚点差分
  → delta_xyz + delta_rot
  → apply_delta_pose(ref_arm_xyz, ref_arm_quat, delta_xyz, delta_rot)
  → CartesianCommandLimiter（线/角速度与加速度限制）
  → movep_follow_xyz_quat
```

由于 `suppress_rotation_during_translation=False`，`delta_rot` 不再乘平移速度相关的衰减系数，平移和旋转可以同时生效。姿态仍受 `rot_deadband_rad`、`max_rot_offset_rad`、最大角速度和最大角加速度约束，不是无约束直通。
