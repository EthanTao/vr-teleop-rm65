# 真机安全与故障处理

本页是**真机操作页**：默认真机控制链、DLS 奇异保护、故障解锁流程、上机自检清单。

> 适用入口：`scripts/hardware/teleop_realman_rm65_safe_hardware.py`（推荐真机入口）。
> 依据代码：`xrobotoolkit_teleop/hardware/realman_rm65_safe_teleop_controller.py`、`hardware/damped_ik.py`、`hardware/realman_udp_feedback.py`、`hardware/cartesian_command_limiter.py`。
> **代码为准，本页只做操作说明。**

> ⚠️ **本页描述的保护不等价于碰撞检测或现场安全认证，不能替代实体急停和现场安全管理。**

## 1. 默认真机控制链：`damped_ik_movej_follow`

2026-09-19 起默认真机模式已切换为 DLS 受限关节跟随。数据流：

```
手柄增量 → 侧装映射 + Grip 锚点 → TCP 速度/加速度限制
  → 官方 FK + 显式工作/工具帧变换 → 6×6 数值雅可比
  → SVD 风险检测 → 降速与 DLS 局部关节增量
  → 限位、局部路径、实际反馈、耗时检查
  → movej_follow 关节目标 → UDP 实测反馈
```

关键设计：

- **实际发送的是检查后的六关节目标 `(6,)`**，不是"给原始笛卡尔目标打个风险标签后照常下发"。这样才真正约束控制器内部的逆解分支。
- 首个目标从**实测关节**开始，后续从**上一已接受目标**继续，同时限制目标相对最新实测关节的偏差。**不会调用全局 IK 选择另一套肘部构型。**
- 实际可达的 FK 位姿用于更新限幅器，**避免目标在保护期间持续累积**。

### 1.1 启动门槛（fail-closed）

- 运行容器必须安装与控制器**兼容的睿尔曼 API2 Python SDK**，使用 RM65-B 官方 FK。缺少 SDK 时**直接拒绝启动，不回退到 `movep_follow`**。
- 启动时只读获取**实际 DH 与当前工具参数**用于本地官方 FK。显式 `--dls-flange-to-tcp` 优先；`--dls-work-from-base` 保持显式配置，**不按当前姿态自动拟合**。
- 读取失败、SDK 读回不一致，或 **FK 与同帧 UDP TCP 相差超过 `5 mm / 2°`** → 拒绝启动。
- 现场 RM65-BI 实测 **`d6 = 161.2 mm`**，区别于标准 SDK 默认的 144 mm；`finger` 工具也不是单位变换。该 17.2 mm 差值即当时 FK/UDP 位置偏差的完整解释。

> `5 mm / 2°` 检查能发现明显不一致，**不是标定正确性的充分证明**。

### 1.2 坐标系配置

```text
T_work_tcp = T_work_base × T_base_flange(q) × T_flange_tcp
```

`--dls-work-from-base` 与 `--dls-flange-to-tcp` 各接受七个数 `x y z qw qx qy qz`，**平移单位为米**。省略时为单位变换，即假设官方 FK 的基座/法兰帧就是控制器使用的工作/TCP 帧。装有灵巧手或使用自定义工作坐标系时，应填写现场已有的正确变换；**不要用单个位姿强行对齐来代替标定**。

官方 SDK 接口要求关节输入为**度**，`flag=0` 返回 `[x,y,z,w,x,y,z]`；内部控制与测试统一使用**弧度、米和 `wxyz` 四元数**。

## 2. 风险判据与停止行为

| 判据 | 降速起点 | 危险区 |
|------|---------|--------|
| 归一化雅可比 `σ_min/σ_max` | `0.04` | `0.01` |
| J3、J5 距零位 | `15°` | `5°` |

- 雅可比**平移部分先除以 `0.3 m`**，再计算 `σ_min/σ_max`。**这与旧版未归一化 URDF 雅可比的阈值不能混用。**
- 关节机械限位预留 `5°` 余量；**已在余量区内时允许退回**。
- 阻尼随风险增大；候选关节增量先限速、平滑变化，再按协议 `0.001°` 量化并检查。
- 危险区**阻止继续深入**，检查局部路径的**四个有序采样点**并**禁止 J3/J5 穿越零位**。满足所有限制的退出方向可低速通过。
- ⚠️ **不能承诺"任意手柄反向动作都能退出"** —— 精确奇异姿态存在无法实现的末端方向。
- 这里检查的是**离散局部关节路径**。`movej_follow` 的实际插值与停止过程由控制器执行；**不提供碰撞检测、自动换肘姿态、全局绕路或实测停止距离保证。**

### 2.1 `[DLS] hold_*` 与故障锁存的区别（重要）

| 现象 | 性质 | 恢复方式 |
|------|------|---------|
| `[DLS] hold_*` | 请求**软停止**，清空已接受关节目标与限幅器速度，等待实测静止后重新计算 | **不需要按 B** |
| `[SAFETY]` 锁存 | 硬停止 `set_arm_stop` + **故障锁存** | 走 §4 四步解锁 |

**单纯 HOLD 不锁存故障。** 但停止未确认、反馈失效、帧不匹配或计算超时**仍会锁存**。正常 B 回位、自检、故障解锁后重新握 Grip，都经过**同一发送门槛**。**B 解锁不会消除奇异姿态，也不会绕过仍然存在的控制器报警。**

## 3. 为什么会"卡死"

程序里有两类停止，表现完全不同：

| 现象 | 触发 | 恢复 |
|------|------|------|
| 松手就停，扣上还能动 | 正常松开 Grip → 软停止 `set_arm_slow_stop` | **不用解锁**，重新扣 Grip 即可（用最新实测位姿重新建锚点） |
| 怎么扣都不动，终端打 `[SAFETY]` | 安全故障 → 硬停止 + **故障锁存** | 走 §4 四步解锁 |

触发硬停止并锁存的情况：UDP 反馈超时（默认 `0.20 s`）、关节超速/越界、控制器错误码、TCP 跟踪误差超限、XR 追踪超时或单帧跳变、目标越出 XYZ 边界、通信失败。

> **锁存 ≠ 只停一下。** 锁存后程序不再下发任何运动目标，锁一直保持到人工解锁为止。

## 4. 解锁四步（顺序不能变）

```
① 松开 Grip（扳机）—— 一点都别扣
② 按一下 B 键 —— 松开再按，不是长按
③ 等这行字出现：
   [SAFETY] re-arm acknowledged; press Grip again to move
④ 再扣一次 Grip —— 机械臂才恢复跟随
```

没出现 ③ 就说明**条件没到，先找原因，不要反复猛按 B**。

### 第 1 步：完全松开 Grip

故障锁存那一刻软件已把"握持中"状态强制清掉，但它还必须**亲眼看到** XR 上报的 Grip 值 ≤ `grip_off_threshold`（默认 `0.15`）才会记为"已松手"。

- 扣着不动，后面按 B **一律无效**。
- 阈值可用 `--grip-off-threshold` 改。

### 第 2 步：按一下 B 键

- 必须是**一次新的按下（上升沿）**。故障时 B 正好被按住的那次不算，要松开再按。
- 按钮名默认 `B`，可用 `--reset-button` 改。
- 此状态（`_rearm_required=True`）下程序每周期只处理解锁判断，**不会下发运动指令**，所以这时候扣着 Grip 也不会动。

### 第 3 步：B 按下瞬间必须同时满足三条

| 条件 | 默认值 | 参数 |
|------|--------|------|
| UDP 反馈线程无错误 | — | — |
| 最新反馈帧足够新 | ≤ `0.20 s` | `--udp-feedback-timeout-s` |
| 反馈无错误码、关节角在限位内 | — | — |
| 六个关节速度全部够慢 | ≤ `1 °/s` | `--rearm-stationary-speed-rad-s` |

任一条不满足，终端打印：

```
[SAFETY] B ignored: wait for fresh, error-free, stationary joint feedback
```

**这不是 B 键坏了，是条件没到。** 等机械臂真正停稳、反馈恢复正常，再按一次。

### 第 4 步：看到确认行才算成功

```
[SAFETY] re-arm acknowledged; press Grip again to move
```

此时故障锁存被清除、锚点被清空。**再扣一次 Grip**：第一个握持周期只做"用最新 UDP 实测 TCP 位姿重新建锚点"，**不会立刻下发运动目标**。这只说明锚点不会沿用旧值，**不能据此保证后续关节不突变**。新默认 DLS 路径从实测关节起步，检查每周期步长与局部奇异风险后才允许发送。

### 解锁失败排查

| 现象 | 原因 | 处理 |
|------|------|------|
| 一直打 `B ignored: ...` | 机械臂还没停稳，或反馈断了 | 等停稳；查 8089 UDP 反馈是否在推送（容器端口映射、`tcpdump -i any udp port 8089 -n`） |
| 按 B 完全无打印 | B 不是新的按下沿（一直按着）；或按钮名不对 | 松开 B 再按；确认 `--reset-button` |
| 解锁成功但立刻又锁存 | **根因没修**：网络抖动、XR 丢失、控制器报警仍在 | 先看 `fault_reason` 属于哪一类，修好链路/清掉控制器报警再解锁 |
| 机器人本体报错 `RM65 reported error codes: [...]` | 控制器报警未清 | 先在睿尔曼侧清除控制器报警，否则第 3 步永远过不了 |

> ⚠️ **解锁只清锁存，不修根因。** 不修根因的话，按 B 要么被拒，要么解锁后同一原因再次触发硬停止。

## 5. ⚠️ 别乱按 B

**没有故障的时候，B 键不是解锁，是"回启动姿势"。**

- 按下 B 会让机械臂按 `--reset-duration-s`（默认 `3.0 s`，为**最短插值时长**）尝试回到**程序启动时记录的 TCP 位姿**。
- 复位先软停止并清空锚点，会打断当前握持；每个回程目标也经过 DLS 门槛，受阻时**不会硬穿奇异区域**，持续无法到达会**超时锁存**。
- 启动位姿是程序开机时从 UDP 抓的**实测姿态**，程序**不会**根据工作半径自动生成安全 Home Pose —— 所以按 B 之前**必须确认回程路径上没有人、没有障碍**。

> **结论：只在需要复位、或终端明确处于故障锁存状态时才按 B。**

## 7. 验证顺序（必须按序）

```bash
# ① 只读 TCP 预检：不发送运动指令
python scripts/hardware/preflight_realman_rm65.py --arm-host 192.168.10.18 --arm-port 8080

# ② Dry Run：执行同一套计算与检查，但不发送运动目标或停止命令
python scripts/hardware/teleop_realman_rm65_safe_hardware.py \
  --arm-host 192.168.10.18 --dry-run --log-motion-debug \
  --motion-log-path /workspace/logs/dls-dry-run.jsonl

#   或一键菜单 2（Dry Run）
python teleop.py --mode hardware-dry-run

# ③ 帧一致性复验（不启动 XR、不发送运动命令）
ssh rm "sudo docker exec -w /workspace xrobo-vr-teleop \
  python scripts/hardware/check_realman_dls_frames.py"

# ④ 有急停、净空与现场监护的条件下，做低速、小范围验证
```

**Dry-run 的预期现象**：真机保持不动时，连续远移手柄会触发"目标与实测关节偏差超限" —— 这是**预期门槛，不表示映射失败**。

**日志字段语义**：

| 字段 | 含义 |
|------|------|
| `command_xyz` | 进入 DLS 的**末端目标**（**不是实际执行反馈**） |
| `joint_candidate_rad` | 检查后的候选关节 |
| `dls_achieved_xyz` | 候选关节的可达末端位置 |
| `joint_target_accepted` | **本地接受**，不代表机器人已执行到位 |
| `dls_status` / `dls_fk_calls` / `dls_candidate_attempts` / `dls_elapsed_ms` | 预算、候选和耗时核对 |
| `singularity_zone` / `sigma_min` / `sigma_ratio` / `severity` / `speed_scale` / `damping` / `step_scale` / `inward` / `hold` | 奇异保护诊断 |

**`--motion-log-path` 的 dry-run 观测字段**：`xr_delta_m`（轴映射后、未缩放/死区的手柄相对位移）、`target_delta_m`（缩放、包络、死区及可选 XY 反向后的目标位移）、`target_xyz_m`（限速前目标）、`command_xyz_m`（限速后候选命令）、`udp_xyz_m`（实际反馈），单位均为米。`target_rotvec_deg` 是**相对旋转向量（轴×角度）非欧拉角**；绝对目标/命令姿态采用 wxyz 四元数。**候选命令预览发生在发送/官方 IK 检查前，不代表已接受或已执行。**

> ⚠️ 控制周期仍为 `20 ms`，DLS 默认在 `18 ms` 前 fail-closed。单帧超预算不发送新目标并保持上一已接受目标，连续 3 帧才 slow stop。旧 74-FK 路径实测完整周期 **38.2 ms**；降至正常 14 / 硬上限 16 次 FK 后，目标容器 1000 周期完整 `_send_motion` Dry Run 为 median **10.169 ms**、P95 **11.782 ms**、max **14.397 ms**，在该条件下满足 18/20 ms 时序预算。该 benchmark 禁止实际下发，不能外推为真实运动验收。

## 9. 已知边界（不要把"主机测试通过"当作真机验收）

- 当前实现是**局部**奇异区域约束，**没有**全局换肘、绕路规划、碰撞检测，也**没有**控制器实际插值的连续路径证明。
- 控制器已有报警仍须按原安全流程处理，**不能通过 B 或放宽阈值绕开**。
- `movej_follow` 的关节目标发送成功**仅表示本地提交**，不等同于执行完成。
- 仿真仍是 Placo / 官方连续 IK 两个后端，**尚未接入此 DLS 后端**；不能把仿真结果当作新真机路径的验收。
- 截至 2026-09-23，**真机最终验收仍未完成**：bounded-search 已通过本机测试、FK 计数和目标容器 1000 周期 Dry Run 时序验证；真实 `movej_follow` 发送、XR 完整主循环、逐轴方向、复位、跟随手感、长时间运行和物理安全仍待验收。
