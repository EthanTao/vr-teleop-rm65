## 诊断「真机验收不完美 → 工程化不可行」，补上「机器人上跑的是哪一版」这个缺口

### 触发

用户报告：真机验收结果「还是不太完美」（现象选「手在动、臂不动 / 跟不上」），并据此判断
「工程化落地完全不可行」，依据是「能跑，但达不到能交付 / 能采数的稳定度」，且现场
**没有留下任何日志**。

### 结论先行

1. **「手在动、臂不动」不是新问题** —— 它正是 2026-09-26 晚 v2.2（见 [2026.9.26.md](2026.9.26.md)）
   针对的现场现象，当时已定位出三个叠加机制并全部改掉。
2. 但 **v2.2 在那时还没有提交**：最后一次动 `damped_ik.py` 的提交是 `52e1a3f`（9.26 demo
   快照），其中 v2.2 标记数 **0**；本地工作树里是 **9**。
3. 于是「验收不完美」有两种解释 —— ①容器里还是旧版；②改动生效了但问题还在 ——
   而**当时手上没有任何证据能区分它们**。现场核对发现：既没有 v2.2 同步到远端的记录，
   也没有任何机制能在事后回答「容器里是哪一版」。
4. 所以这次验收的结论**不足以支撑架构级判断**。缺的不是算法，是**版本可追溯性**。
5. 本次先补三件事：提交 v2.2（`059d5cb`）、两端打印控制链源码指纹、修掉测试污染。

### 诊断过程中被推翻的错误结论（如实记录）

中途曾把 `%TEMP%\vr-teleop-rm65.manifest.json` 的空内容（40 字节：
`{"files": {}, "signatures": {}}`）当作「同步静默无操作」的证据，并据此刻画了
「同步脚本打印 `[OK]` 但什么都没传」的风险。**该结论已撤回**：

- **复现**：单独跑 `tests/test_teleop_launcher.py -k skips_upload_when_remote_is_current`，
  该文件内容与体积不变、mtime 更新为当前时间。
- **根因**：该用例把 `_iter_source_files` 打桩成 `[]`、远端清单打桩成空，却**没有打桩
  `_save_manifest`**，于是真的把空清单写进了 `LOCAL_CACHE`。`tests/conftest.py` 第 12-14 行
  已经记录过这一类污染。
- **附带事实**：`LOCAL_PATH` 是 `Path(__file__).resolve().parent`（与 cwd 无关）；本地实跑
  `_iter_source_files()` 稳定返回 **115 个文件、115 个有签名**。所以空清单不可能来自当前
  代码的同步路径。
- **教训**：那份文件根本不能当作「上次同步的痕迹」—— 任何一次 `pytest` 都会覆盖它。

边界（同时写进模块 docstring）：指纹只证明**源码字节一致**，不证明行为一致；不覆盖
`config/` 快照、容器里的 Python 版本与已装依赖、运行时 CLI 参数；**不进控制链**，
不参与任何安全判据、阈值、锁存或发送流程。

### 整理过程中浮现的关键结论（本文首次串联，仍需现场验证）

```

  = 目标每周期落在可达范围外 → 每周期保持 → 「手在动、臂不动」
```

显式对上 —— **该日志当天就预测了这个后果**，并把它列进了「临时缓解 / 根因修复」的下一步。

- **含义**：换成 v2.2 不能治愈它 —— v2.2 改的是「同一条不可达方向上怎么停」，
  不是「让那个方向变可达」。
