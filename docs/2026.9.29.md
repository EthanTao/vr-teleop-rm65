### 结论先行

1. **「手在动、臂不动」不是新问题** —— 它正是 2026-09-26 晚 v2.2（见 [2026.9.26.md](2026.9.26.md)）
   针对的现场现象，当时已定位出三个叠加机制并全部改掉。
2. 但 **v2.2 在那时还没有提交**：最后一次动 `damped_ik.py` 的提交是 `52e1a3f`（9.26 demo
   快照），其中 v2.2 标记数 **0**；本地工作树里是 **9**。
3. 于是「验收不完美」有两种解释 —— ①容器里还是旧版；②改动生效了但问题还在 ——
   而**当时手上没有任何证据能区分它们**。现场核对发现：既没有 v2.2 同步到远端的记录，
   也没有任何机制能在事后回答「容器里是哪一版」。
4. 所以这次验收的结论**不足以支撑架构级判断**。缺的不是算法，是**版本可追溯性**。
5. 本次先补三件事：提交 v2.2（`059d5cb`）、两端打印控制链源码指纹、修掉测试污染。

### 诊断过程中被推翻的错误结论（如实记录）

中途曾把 `%TEMP%\vr-teleop-rm65.manifest.json` 的空内容（40 字节：
`{"files": {}, "signatures": {}}`）当作「同步静默无操作」的证据，并据此刻画了
「同步脚本打印 `[OK]` 但什么都没传」的风险。**该结论已撤回**：

- **复现**：单独跑 `tests/test_teleop_launcher.py -k skips_upload_when_remote_is_current`，
  该文件内容与体积不变、mtime 更新为当前时间。
- **根因**：该用例把 `_iter_source_files` 打桩成 `[]`、远端清单打桩成空，却**没有打桩
  `_save_manifest`**，于是真的把空清单写进了 `LOCAL_CACHE`。`tests/conftest.py` 第 12-14 行
  已经记录过这一类污染。
- **附带事实**：`LOCAL_PATH` 是 `Path(__file__).resolve().parent`（与 cwd 无关）；本地实跑
  `_iter_source_files()` 稳定返回 **115 个文件、115 个有签名**。所以空清单不可能来自当前
  代码的同步路径。
- **教训**：那份文件根本不能当作「上次同步的痕迹」—— 任何一次 `pytest` 都会覆盖它。

1. **`0 -30 -90 0 90 0` 把所有方向的下限从 6.5 cm 提到 14.0 cm**（2.15 倍），

## 目标澄清：手柄 → 灵巧手 → 充电枪插拔；新增 UDP 原始帧只读探针

### 用户澄清的目标与四条硬约束

最终目标是**用手柄控制机械臂末端的灵巧手完成充电枪插拔**。据此确认：

| 项 | 现状 | 影响 |
|---|---|---|
| 六维力传感器（F/T，选配） | **没装，也暂时不打算加** | 力控没有硬件基础，只能走「电流代理 + 位置策略」 |
| 充电枪安装方式 | **灵巧手握着枪** | 插拔力全部经灵巧手传递；工具帧（法兰→枪尖）随握持变化 |

### 结论：位置跟随做到完美也插不进去

工程研究给出的量级（《电动汽车自动充电连接器柔性对接机构设计研究》，
汽车工艺与材料 2025(3):48-54）：**插拔力 < 140 N**（标准要求）；
其 **4 自由度柔性对接机构**可在**定位偏差 10 mm / 角度偏差 5°** 下工作 ——
注意这是**装了被动柔顺之后**的容限，硬对硬的容差要小一个量级。

因此当前链路的缺口不是精度，而是三层能力：

| 能力层 | 作用 | 仓库现状 |
|---|---|---|
| 力觉 | 判断「顶上了没有、顶多大」 | 全仓无 F/T、无力控、无力位混合 |
| 柔顺 | 横向让位、轴向受控进给 | 无导纳 / 阻抗 / RCC |
| 灵巧手控制 | 握枪 / 扳锁扣 | `common/base_teleop_controller.py:420` 只有 `# TODO: add dexterous hand support` |

### 由此确认的一条会立刻咬人的行为（本次新增结论）

按源码逐层核对（`realman_rm65_safe_teleop_controller.py:1107-1115`）：

```
接触后手柄继续前推 → 命令相对实测偏差上升
  → 超过软线（1 个周期额度，J1/J2 = 0.360°）按余量降速
  → 到保持线（2/3 × 余量 = 0.720°）冻结命令流 + 软停止
  → 保持持续 > --tracking-lag-hold-dwell-s（默认 0.30 s）

  → _latch_safety_fault("DLS 拒绝本次运动：…")   ← 硬停 + 故障锁存
```

= `0.12 s`）。

**这是设计选择而非缺陷**：自由空间里「一直顶着就停」是对的，插拔里它是错的。
所以要新增的是**接触模式**，不能靠放松既有安全逻辑。

## 逐轴方向定案：新增「手柄 → 末端」映射矩阵最小二乘估计

### 背景

「哪根手柄轴对应末端哪根轴、符号对不对」在项目里悬了几周没有定案：
`docs/RM65参数与坐标系.md` §14.2 的真机观测栏靠口述；2026-09-18 的观测（左右→X、上下→Y）
与代码推导（上下→X、左右→Y）**正好互换**，两边都没有仪器读数。
而这件事是工程化验收的地基 —— 数据集方案里写着「方向没定案前采的数据全部作废」。

### 关键观察：不需要额外试动作，日志里两层都有

- `xr_pose` 存的是**原始 SDK 手柄位姿**（`realman_rm65_safe_teleop_controller.py:2015-2017`，
  坐标变换**之前**的那一个），形如 `[x, y, z, qx, qy, qz, qw]`；
- `target_xyz`（映射层）与 `measured_tcp_xyz_m`（端到端）是末端位姿。

于是解一个最小二乘即可拟合映射矩阵 `Δ末端 ≈ M · Δ手柄`：每列绝对值最大的那项就是
**该手柄轴的落点轴**，它的符号就是**方向正负**。

代码里的期望值（`:531-572`）：`Δ_tcp = diag(scale) · R · Δ_hand`，
`R = [[0,1,0],[1,0,0],[0,0,-1]]`、`scale = 1.0`、`deadband = 0`、`invert_tcp_xy = False`
⇒ 期望 `Δtcp_x = Δhand_y`、`Δtcp_y = Δhand_x`、`Δtcp_z = −Δhand_z`。

### 交付

- `xrobotoolkit_teleop/utils/mapping_estimation.py`（新增，逻辑可单测）
  - `collect_pairs()`：只取同一段内、周期连续的两帧；剔除单帧手柄位移 < `2 mm` 的样本
    （噪声主导）与手柄姿态变化 > `0.02 rad` 的样本（旋转耦合进平移）。
  - `fit_matrix()`：`lstsq` 解 `Δ末端 ≈ M · Δ手柄`，给出样本数、残差 RMS、R²。
  - `axis_verdict()`：每根手柄轴的落点轴 + 符号 + 占该列比例。**对整体缩放不敏感** ——
    这是关键：笛卡尔限速器会把系数整体压小，看系数绝对值会误判。
  - `compare_verdicts()`：与代码期望逐轴比对，明确列出「落点轴不同 / 符号相反」。
  - `analyse()` 同时给**映射层**与**端到端**两份结果；两层落点轴一致才说明整链一致。

## 验收证据完整性：日志被截断会静默通过（补第一条判据）

### 背景

上一节的判据表已经能判「跟随比 / 锁存 / 方向」，但**证据本身是否完整**没人检查。

`MotionLog`（`hardware/motion_diagnostics.py`）只在**正常关闭时**写一行收尾：

```python
batch.append({"type": "log_end", "dropped_rows": self.dropped_rows, "error": self.error})
flush()
```

而且 `close()` 在「有丢行或写入出错」时会**抛 `RuntimeError`**（刻意的 fail-closed）。
但只要进程被强杀、掉电、或收尾时异常，`log_end` 就不会被写出来 —— 而此前的
`load_cycles()` 只挑 `type == "cycle"` 的行，于是**一份被砍掉一半的日志看起来与完整的
完全一样**，照样能算出一张漂亮的判定表。这正是「静默信任不完整证据」。

### 改动

- `xrobotoolkit_teleop/utils/motion_log_analysis.py`
  - 新增 `load_log()`：返回 `(周期行, 解析错误, log_end 行)`；`load_cycles()` 保留为兼容包装。
  - `analyse()` 新增 `log_end` / `log_dropped_rows` / `log_error` / `log_complete`
    （`log_complete` = 有收尾行 **且** 无丢行 **且** 无写入错误）。
  - `format_report()` **先报完整性**：缺 `log_end` 或有问题时打印警告行。
- `xrobotoolkit_teleop/utils/acceptance_criteria.py`
  - 新增判据 `require_complete_log`（默认开），并把它放在**第一条** ——
    证据不可信，后面的数字都没有意义。
- 测试：`tests/test_motion_log_analysis.py` +5 条、`tests/test_acceptance_criteria.py` +5 条
  （缺收尾行 / 有丢行 / 有写入错误 / 显式关掉该判据 / `load_log` 返回值）。

§7.1 里的三条分析命令也同步改成 `<同一时间戳>`。

### 验证状态

- **本机单测**：`python -m pytest tests -q` → **529 passed**（改动前 519）。
- **格式**：`black --check --target-version py313` 通过。
- **未验证**：没有真机日志；「被截断的日志」是用构造数据验证的，不是现场遇到过的。

### 这一条为什么值钱

前几周的验收全是口述；现在的风险换成了「**有日志，但日志不可信**」。
把完整性排成第一条判据，等于给整套判定加了一道**证据闸门** ——
只要程序不是干净退出的，判定必然不通过，不会出现「看着挺好、其实只有一半数据」。

### 同一类陷阱的第二条：dry-run 日志被当运动验收判

`--dry-run` 下机械臂根本不运动，`measured_tcp_xyz_m` 恒定，跟随比必然接近 0。
此前的判据表只会给出满屏 ❌（跟随比 `0.00`、最差段 `0.00`），**却不说「这根本不是一次
运动验收」** —— 报告读起来像「遥操作做得很差」，实际是「跑错模式了」。
运动日志里本来就有 `dry_run` 字段，只是没人用它。

- `acceptance_criteria.py` 新增判据 `require_live_run`（默认开），排在证据完整之后；
  读 `motion_report["dry_run"]`（`analyse()` 记成「出现过的取值集合」）。
  **日志里没有该字段时按「不是真实运行」处理（fail-closed）**。
- `tests/test_acceptance_criteria.py` 新增 4 条：dry-run 判不过且原因明确、live 通过、
  显式关掉后可做 dry-run 诊断、缺字段时 fail-closed。
- `docs/真机安全与故障处理.md` §7.1 判据表新增该行。

**验证**：`python -m pytest tests -q` → **533 passed**（本轮 519 → 533）；
`black --check --target-version py313` 通过。

### 小结：这一轮（2/15）做的两件事

两条判据都不是「让算法更好」，而是**让报告不撒谎**：

| 判据 | 防止的假象 |
|---|---|
| 日志证据完整 | 「看着挺好，其实日志被砍掉了一半」 |
| 为真实运行（非 dry-run） | 「看着像遥操作很差，其实是跑在 dry-run 模式」 |

真机两侧（`--motion-log-path`、`--log-motion-debug`）的行为一行未改，只动了离线分析层。
