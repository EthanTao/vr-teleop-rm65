## 4. 图像采集的数据流与容量

```text
D435i → USB → 独立相机进程：pyrealsense2
                    ├─ 原始彩色 / 深度 + 各自时间戳 → 有界写队列 → 相机文件
                    └─ 小型元数据 / 最新观测 → 同步器或后续视觉模块

RM65 → 已有唯一 UDP 接收器 → latest → 现有 50 Hz 安全与控制循环
                          └─ 非阻塞小型反馈副本 → 历史缓存 / robot_states.jsonl

会话协调器 → 分配同一个 session_id → 启动 / 关闭各记录者 → 全部关闭后封存
离线同步器 → 相机索引 + 状态历史 + 时钟模型 → 配对表 → 手眼标定 / 数据集
```

相机等待、像素复制、对齐、棋盘检测、压缩和磁盘写入均在控制循环外。接收侧新增通道也不能等待相机或执行复杂回调；进程隔离仍共享 CPU / 内存 / 磁盘，需测资源竞争和控制周期尾延迟。

建议从官方示例使用的 **640×480、30 Hz** 组合开始，启动前枚举该设备实际支持的 profiles；指定序列号，避免接错相机。

| 数据 | 格式 / Shape | 语义 |
| --- | --- | --- |
| 彩色原始帧 | `uint8 (480,640,3)`，`bgr8` | OpenCV 输入；给训练模型前显式转换 RGB，并记录通道顺序 |
| 原始深度 | `uint16 (480,640)`，`z16` | 乘现场 `get_depth_scale()` 得 m，不把 0.001 写死；0 为无效深度 |
| 对齐深度（派生，可选） | `uint16 (480,640)`，对齐到彩色像素网格 | 用 `rs.align(rs.stream.color)` 生成；保留原始深度及生成参数，不覆盖原始证据 |
| 内参 | 每个视频 profile 的 K `(3,3)`、畸变模型与系数 | 绑定分辨率、流及裁剪/缩放；尺寸改变后不能沿用旧 K |
| 相机内部外参 | 原生 depth → color 的 R `(3,3)`、t `(3,)`，m | `get_extrinsics_to`；这是两成像器之间的变换，不是相机 → 法兰的手眼标定 |

以上 SDK 接口与格式依据[官方对齐示例](https://github.com/realsenseai/librealsense/blob/master/wrappers/python/examples/align-depth2color.py)和[投影说明](https://github.com/realsenseai/librealsense/wiki/Projection-in-RealSense-SDK-2.0)。第一阶段不启用 IMU，不把 IMU 标定作为 RGB-D 与手眼接入的前置条件。

SDK 回调只交接帧或必要元数据。若 NumPy 视图跨出帧生命周期，必须保留 SDK 帧所有权或复制到自有缓冲；不能把底层已释放的数据交给异步写者。[官方帧管理说明](https://github.com/realsenseai/librealsense/blob/master/doc/frame_lifetime.md)。在线消费只保留最新观测；记录队列先取 8 组上限，满时记录丢帧数量、帧号和时间范围，绝不阻塞安全接收器或机械臂控制。

容量估算（不含 SDK 缓冲和 Python 对象）：每组原始 BGR + 深度为 `640×480×(3+2)=1,536,000 B`；30 Hz 为 **46.08 MB/s、约 2.76 GB/min**，8 组约 12.29 MB。若再存同尺寸对齐深度，增加 18.43 MB/s。先采用分块无损存储、编码在写进程，测磁盘持续吞吐后再选压缩；深度不能保存成有损 JPEG 或仅有颜色的可视化图。

逐像素复制/对齐复杂度 O(HW)，记录缓冲 O(QHW)；控制侧只传帧 ID、时间与状态引用，不传大图。正常关闭要释放 pipeline 并等待写者退出；拔线/超时生成相机错误及不完整记录，重连建立新时间段，不能延用旧配对。

## 5. 时间同步：先定义时钟，再谈误差

### 5.1 三种不同的问题

1. **像素对齐**：depth 与 color 的空间对应，`rs.align` 解决此问题。
2. **流间配对**：某张 color 与哪张 depth 对应；SDK frameset 提供配对，但仍须保存各流的帧号、时间戳及时间差，不能推定曝光完全同时。
3. **图像—机器人配对**：在图像对应时刻求机械臂实测位姿，需要统一时钟、历史反馈及延迟评估。30 Hz 相机与 50 Hz 控制不必同频，也不能按循环编号直接对齐。

### 5.2 原始时间字段

每流保存 `frame_number`、`sdk_timestamp_ms`、`timestamp_domain`、`host_received_monotonic_s`、`clock_epoch_id`、元数据可用性、实际曝光信息及丢帧计数。SDK `get_timestamp()` 单位为 ms；`SENSOR_TIMESTAMP` 元数据描述曝光中点，单位为 μs；二者语义与时钟映射不能混为一谈。支持元数据需逐帧 `supports_frame_metadata` 检查，不可用就保存 null。[官方时间戳定义](https://github.com/realsenseai/librealsense/blob/master/include/librealsense2/h/rs_frame.h)、[Python frame API](https://realsenseai.github.io/librealsense/python_docs/_generated/pyrealsense2.frame.html)。

`host_received_monotonic_s` 在应用回调入口或取帧返回后立即记录，表示应用观察到该帧的时刻，不能称为内核 USB 到达时间或曝光时间；处理/写盘完成时刻另记，不覆盖它。

机器人侧保存 `sample_id`、`received_monotonic_s`、实测 q/qdot、TCP 和错误。**当前解析结果没有控制器采样时刻**：接收时间包含控制器推送、网络和调度延迟；SDK 开启 global time 不能消除这部分误差。

### 5.3 推荐映射与失效处理

- **同一 Linux 主机优先**：核对各进程的 `clock_id`、系统启动标识与时间命名空间，确认使用同一单调时间基准。仅“两个容器”不等于两台独立时钟主机。
- **支持 GLOBAL_TIME 时**：对实际 sensor 检查 `supports(rs.option.global_time_enabled)`、设置并读回选项，同时检查每帧实际 domain。该模式是把设备时钟换算为 OS system clock，不是主机 `monotonic`，也不是机械臂硬件同步。[SDK 定义](https://github.com/realsenseai/librealsense/blob/master/include/librealsense2/h/rs_frame.h)、[选项 API](https://realsenseai.github.io/librealsense/python_docs/_generated/pyrealsense2.option.html)。
- **桥接 system → monotonic**：周期性夹取 `m_before → realtime → m_after`，用单调中点与 realtime 建对应关系并记录夹取区间；校正系统时间跳变，不能只在启动时减一次固定偏移。保留原始时间戳和模型版本，发生跳变/domain 改变/重连则开始新 epoch 并清空待配对缓存。
- **仅 HARDWARE_CLOCK 时**：按流建立 `t_mono ≈ a·(t_device_ms/1000)+b`，记录窗口、漂移和残差。只用主机接收时间拟合时，传输偏置无法与真实偏移完全分离；低延迟包/稳健拟合只能改善估计，不能据小残差声称曝光级精度。
- **只有接收时刻或映射未稳定**：保留原始记录并标为 `arrival_only` / `unsynchronized`，不生成已验证动态位姿配对。曝光中点元数据若使用，还需明确其单位、所属时钟及与映射的关系；不能直接与 global-time 数值相减。
- **相机与机器人固定延迟**：用独立的动态视觉—运动观测或仪器评估端到端偏差；不能拿 USB/网络往返时间的一半直接当单向采样延迟。未测之前保存不确定性，静态手眼采样用于降低时间误差影响。

### 5.4 配对算法与误差预算

接收器外建立约 5 s 的机器人历史缓存。离线按统一后的图像时刻找前后两帧；位置线性插值，姿态使用归一化、最短路径四元数 SLERP。输出前后 sample ID、时间权重、包间隔、时钟模型、质量标记，插值结果是估计，不能称为该时刻直接实测。

遇到缺少前/后帧、断流、故障、时钟 epoch 变化或超限间隔，输出 `valid=false`，不外推补齐。初始探索门槛可设前后包跨度 ≤40 ms、同域 RGB-depth 时间差 ≤10 ms，再根据实际有效率与任务预算调整；两项门槛均不证明绝对采样时间准确。顺序数据双指针离线配对 O(N+M)，在线缓存查询可做 O(log M)。

在线视觉若不等待未来反馈，只能使用已到达的历史/最新合法状态，并记录状态年龄；不得把离线双向插值当成实时可获得的观测。数据集分别保留曝光对应状态、观测到达时刻及实际命令发送时刻，防止未来信息进入策略输入。

时间错位带来的目标位置误差可粗略界为 `e_time ≲ v·|Δt| + L·ω·|Δt|`：第一项是末端平移，第二项是相机到关注点的距离 L 在旋转中产生的误差。例如按当前限速 `v=0.05 m/s`、`ω=0.25 rad/s`，取 `L=0.10 m`，错位 20 ms 对应约 **1.0 mm 平移 + 0.5 mm 旋转影响**；此估算不含几何标定、深度与机械误差。若只给时间误差分配 1 mm 预算，在上述条件下约需 `|Δt|≤13.3 ms`，仍须独立测得时序误差才可验收。

## 6. 手眼标定：求相机相对法兰的固定变换

### 6.1 先冻结坐标与工具定义

问题是：相机看见的插座位置在光学坐标系中，而机械臂运动使用控制器工作/基座与 TCP 坐标。需要一条可检查的几何变换链。定义 `^A T_B` 将 **B 坐标中的点转换到 A 坐标**；位置统一 m，旋转用正交矩阵；机器人四元数沿用当前代码 `wxyz`。

| 符号 | 坐标系 |
| --- | --- |
| B / W | 控制器基座 / 当前工作坐标系；侧装不改变变换运算，不能把 B 默认成水平地面 |
| F / T | 机械臂末端法兰 / 当前工具 TCP（例如 `finger`），均不是灵巧手可动指尖 |
| C / D | D435i **彩色光学坐标系** / 原生深度光学坐标系，不能用相机外壳 CAD 原点替代 |
| P | 固定在环境中的标定板坐标系 |

本轮用户确认相机随末端法兰刚性运动，因此保存 `^F T_C`。开始采样前检查支架无松动，读取并保存实际工具帧、工作帧及有效变换，复用既有 FK/UDP 一致性核对。若相机支架之后发生位移，旧标定失效。

本项目几何适配器满足：

```text
^W T_T = ^W T_B · ^B T_F · ^F T_T
因此：^B T_F = inverse(^W T_B) · ^W T_T · inverse(^F T_T)
```

`^W T_T` 来自经过帧核对的真实 UDP TCP；另外两项来自本轮实际控制器/配置快照。不能因字段名叫 TCP 就直接当作法兰，不能将 work 位姿直接标成 base，也不能用发送目标或 Meshcat URDF FK 填入实测样本。

### 6.2 采样与求解

1. 在环境中固定尺寸实测过的刚性棋盘，棋盘方格边长以 m 记录。使用与任务相同的彩色 profile、正确 K 和畸变模型；SDK 内参是起点，仍需用多视角重投影检查。不要把未知 SDK 畸变模型的系数直接塞进 OpenCV；先核对模型，必要时正确去畸变或独立标定。
2. 通过现有安全遥操作链移动到多个可见标定板的姿态，**到位静止后**采图和实测反馈。建议 20–30 个有效姿态、另留 5–10 个未参与求解的姿态；覆盖不同旋转轴与位置，保持板不动，避免只有平移或单轴旋转。此数量是项目起始建议；几何可观测性需另查，不能凭数量通过。
3. 每姿态先观察约 0.5–1 s 的窗口，用 UDP 关节速度、TCP 变化与角点稳定性确认静止，记录窗口和门槛；不以“sleep 已结束”代替静止判定。仍保存帧时间与对应反馈，不用命令目标代表当前姿态。
4. 棋盘角点提取/亚像素细化，`solvePnP` 得到 `^C T_P`；检查可见性、正深度、平面 PnP 多解与重投影残差。若多解无法排除，则拒绝该样本，保留原始图像及拒绝原因。
5. 输入 `cv2.calibrateHandEye`：`R_gripper2base/t_gripper2base = ^B T_F`，`R_target2cam/t_target2cam = ^C T_P`；输出 **`R_cam2gripper/t_cam2gripper = ^F T_C`**，不是其逆。每项 R 为 `(3,3)`、t 为 `(3,1)`；输入是 N 个矩阵/向量列表。比较 PARK 与 TSAI 等方法及重复采样稳定性，不仅选择训练残差最小者。

输入输出方向及非平行旋转轴要求依据[OpenCV 官方 `calibrateHandEye` 文档](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html)。SDK 出厂的 depth/color 内部标定、IMU 标定和本节机器人手眼标定是不同任务，不互相替代。

### 6.3 闭环关系与独立验证

固定棋盘在机器人基座中的位姿应保持一致：

```text
^B T_P(i) = ^B T_F(i) · ^F T_C · ^C T_P(i) ≈ 常量
A_ji = inverse(^B T_F(j)) · ^B T_F(i)
B_ji = ^C T_P(j) · inverse(^C T_P(i))
X = ^F T_C，因而 A_ji · X = X · B_ji
```

这些式子消掉未知的固定棋盘位姿，留下需要求解的相机—法兰关系。先以合成的已知 X 检查代码变换方向、求逆与单位，再用真实数据求解。训练姿态之外检查：棋盘位置与旋转分散、重投影误差、不同姿态子集/重复采集的 X 差异，以及独立固定点的跨视角重建误差；不能只用求解器返回成功作为验收。

标定输出至少保存 `T_flange_color (4,4)`、`T_color_depth (4,4)`、流内参/畸变、序列号、profile、固件/SDK、支架标识、工具/工作帧快照、样本列表、排除理由、算法、训练/留出指标、数据哈希与验证状态。先输出 `build/calibration/d435i/<ID>/`，验收后才注册为可用配置；本轮不创建虚构矩阵。

### 6.4 插座三维点如何进入控制坐标

精确几何路径优先从原生深度像素及其内参反投影得到 `^D p`，再用 SDK depth→color 外参变到 C，最后经手眼及真实法兰位姿变到 B：

```text
^B p = ^B T_F(t) · ^F T_C · ^C T_D · ^D p
```

用彩色图做 PnP 就输出 C 坐标，不能再误乘一次 depth→color。对齐深度可用于彩色 ROI 的筛选与观察；涉及精密坐标时保留原生深度的投影/反投影链和遮挡检查，不仅因图像尺寸相同就混用内参或坐标。[SDK 投影与外参说明](https://github.com/realsenseai/librealsense/wiki/Projection-in-RealSense-SDK-2.0)。

近距离插入时应测手/枪遮挡与插座 ROI 有效深度率；无效深度保留缺测掩码。视觉位姿、深度空洞或电机电流不能作为实测接触力，D435i 接入不改变当前无独立力传感器的边界。

## 7. 会话文件与实现拆分（均为拟新增）

在现有 `build/experiments/<session_id>/` 下增加：

```text
camera/camera.json        # 设备、profile、内外参、曝光/选项、开始/结束及错误
camera/frames.jsonl       # 每流原始帧号、各类时间戳、epoch、文件块/帧内索引
camera/chunks/            # 原始 BGR/Z16 无损块，派生对齐数据单列
robot_states.jsonl        # 接收侧独立反馈，保留来源与接收时间语义
clock_models.json         # 每流/epoch 映射、残差、桥接测量与不确定性
alignment.jsonl           # 帧与机器人前后 sample ID、权重、状态及拒绝原因
```

原有 motion / events / session 不塞像素数组。事件记录 camera_started、camera_stopped、camera_error、clock_epoch_changed、camera_drop。第一版可用顺序帧块与 JSONL；SDK `.bag` 可作为独立调试/回放选项，仍需外部记录机器人状态与时钟关系，不能替代整个实验会话。

封存顺序：停止接收新任务 → 停止相机流 → 写者完成/报告超时 → 生成总结 → 哈希所有已关闭文件。清单升级时兼容旧 v1 五文件格式，新增版本枚举允许的相对文件路径，拒绝越界/符号链接；回收器验证每个块、检测遗漏与截断。相机写者未退出不得宣称完整封存；大文件回收需调整当前 60 s scp 超时并保留失败暂存/重试语义。

| 拟新增 / 修改点 | 职责与边界 |
| --- | --- |
| `scripts/hardware/preflight_realsense.py` | 只枚举设备/固件/USB/profile 与读取配置；不导入或启动机械臂控制，不自动校准/升级 |
